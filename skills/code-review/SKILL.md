# 현재 사용과 다음 변경을 위한 코드 리뷰

지금 쓰는 데 무엇이 걸리는지, 다음 변경에서 어떤 비용을 치르게 되는지 실제 코드로 판단한다. 코드가 기능을 제공하는 방식과 그 기능을 유지·변경하는 데 필요한 지식을 함께 살핀다.

다음 원문을 읽고 리뷰 기준으로 적용한다. 기준을 새로 정의하거나 요약만으로 원문을 대체하지 않는다.

- [feature-future](../feature-future/SKILL.md)의 현재 가치와 다음 변경의 선택권을 판단에 사용한다. 이 참조로 미션 고찰 대화 모드를 활성화하지 않는다.
- [코드베이스 설계](../codebase-design/SKILL.md)의 용어와 깊은 모듈 기준으로 인터페이스의 효용, 변경의 국소성, 교체 지점을 살핀다.
- [경계와 책임](../boundary-responsibility/SKILL.md)에 따라 변경 이유, 지식의 위치, 데이터와 상태의 소유권을 살핀다.

## 범위와 근거 확인

사용자가 지정한 diff, PR, 파일 또는 기능을 대상으로 삼는다. 변경 리뷰라면 기준 버전과 diff를 확인하고, 기존 코드 리뷰라면 지정한 기능의 호출 경로를 확인한다. 범위가 불명확해 결론이 달라질 때만 필요한 범위를 확인한다.

목적과 실제 사용 상황을 기존 요청·문서·코드에서 파악한다. 사용자에게 없는 목적이나 우선순위를 만들지 않는다. 변경 줄만 보지 말고 관련 호출부, 입력과 출력, 데이터 흐름, 상태 갱신, 오류 처리와 기존 검증을 필요한 만큼 읽는다. 변경에서 발견한 기존 문제는 이번 변경이 만든 문제와 구분하고 범위 밖 조사를 무제한으로 넓히지 않는다.

리뷰 요청 자체로 수정·커밋·배포 권한을 얻지 않는다. 읽기 조사와 허용된 검증으로 판단하며, 이미 별도로 받은 수정 권한은 그 범위 안에서 유지한다.

## 판단할 것

### 지금 쓰는 데 걸리는 문제

누가 어떤 입력이나 동작을 했을 때 무엇을 할 수 없거나 잘못 판단하게 되는지 확인한다. 기대한 결과와 실제 코드가 만드는 결과 사이의 차이를 설명한다. 정확성, 오류 복구, 데이터 보존, 응답성 등은 해당 사용 흐름에 영향을 줄 때 살핀다.

가능하면 실제 호출 인터페이스나 사용자 흐름으로 재현한다. 실행하기 어렵다면 문제를 만드는 분기·값·호출 순서를 코드로 추적한다. 정적 분석으로 확인한 문제와 실행으로 관찰한 결과를 구별한다. 빌드 성공이나 테스트 존재만으로 사용 동작이 검증됐다고 판단하지 않는다.

### 다음 변경을 어렵게 만드는 선택

[feature-future](../feature-future/SKILL.md)의 관점으로 현재 제공 가치와 다음 변경의 선택권을 함께 판단한다. 요청·로드맵·기존 변경 패턴·실제 코드의 책임에서 예상할 근거가 있는 변경을 하나 들어 다음을 연결한다.

- 그 변경을 예상하는 근거와 담당 모듈.
- 함께 고쳐야 하는 호출부·정의·저장 데이터와 유지할 수 있는 부분.
- 현재 선택을 되돌릴 때 필요한 이행, 호환성 처리나 재검증 비용.
- 지금 구조를 고치는 비용과 기능 제공을 늦춰 잃는 가치.

미래 요구의 근거가 없으면 만들어 지적하지 않는다. 코드에서 이미 드러나는 지식 분산이나 숨은 사용 조건은 어떤 구체적인 변경에서 비용을 만드는지 설명할 수 있다. 그 변경이 확정된 계획인지 판단을 위한 예시인지 밝힌다. 짧게 쓰고 버릴 기능과 오래 운영할 기능에 같은 구조 투자를 요구하지 않는다. 현재 제약을 받아들일 이유가 충분하면 그 선택을 결함으로 보고하지 않는다.

### 코드가 책임을 잘 담고 있는가

두 설계 스킬의 기준을 실제 호출부와 연결한다. 관련 있는 항목을 확인하며 모든 항목에서 발견사항을 채울 필요는 없다.

- 호출자가 배워야 하는 입력·오류·설정·순서가 제공하는 효용에 비해 과도한가? 단순 전달이나 내부 구현 노출 때문에 복잡성이 호출부로 이동했는가?
- 한 가지 변경에 필요한 지식과 검증이 담당 모듈에 모이는가? 같은 규칙이 여러 호출부에 퍼지거나 독립적으로 바뀌는 규칙이 묶여 있는가?
- 교체 지점이 실제 바뀌는 대상에 놓였는가? 추측한 교체를 위해 인터페이스와 계층을 늘렸는가? 호출자와 테스트가 같은 인터페이스를 사용할 수 있는가?
- 외부 형식의 검증과 내부 모델 변환을 연동 담당이 맡는가? 공통 화면과 계산에 공급자 지식이 퍼지거나 단위·조회 시점·부분 성공의 의미가 사라지는가?
- 원본 상태와 갱신 담당이 명확한가? 파생 상태·캐시 무효화·비동기 결과 순서의 책임이 흩어져 실제 불일치나 수정 누락을 만드는가?
- 오류와 부분 실패를 필요한 수준으로 전달하는가? 호출자가 공급자 예외나 숨은 실행 순서를 알아야만 올바르게 사용할 수 있는가?

설계 기준과 다르다는 사실만으로 결함을 선언하지 않는다. 현재 사용 문제 또는 구체적인 변경 비용으로 이어지는 원인을 설명한다. 취향, 파일 길이, 함수 수, 형식 차이만으로 지적하지 않는다. 개선안도 호출자가 배울 것과 변경 위치를 줄이는지 확인하며, 추측한 미래를 위한 범용화나 요청과 무관한 재설계를 요구하지 않는다.

## 발견사항과 결론

발견사항을 영향이 큰 순서로 보고하고 같은 원인에서 나온 증상은 합친다. 각 항목에 다음 근거를 담는다.

- 심각도와 문제를 드러내는 파일·줄 위치. 긴급은 진행 차단·데이터 손실 등 즉시 대응이 필요한 영향, 높음은 주요 사용 흐름의 실패나 근거 있는 다음 변경의 큰 제약, 보통은 제한된 영향과 수정 비용을 뜻한다. 영향 범위와 발생 조건으로 판단한다.
- 발생 조건, 코드상의 원인, 사용자에게 생기는 결과 또는 다음 변경의 추가 비용.
- 원인을 없애는 최소 개선 방향과 그 방향을 확인할 검증. 실행한 검증과 앞으로 필요한 검증을 구분한다.

코드 위치는 원인을 이해할 수 있는 가장 좁은 범위를 사용한다. 관련 호출부가 결론에 필요하면 함께 연결한다. 미래 비용만으로 지적할 때는 예상 변경의 근거와 수정 범위를 빠뜨리지 않는다. 확인하지 않은 발생 빈도나 비용을 숫자로 만들지 않는다.

재현 결과·코드 근거로 뒷받침한 발견사항과 미확인 가정·질문을 분리한다. 확신이 부족한 의심을 결함으로 올리지 말고 무엇을 확인하면 판단할 수 있는지 남긴다. 발견사항이 없으면 없다고 말한다. 검토한 범위와 실행한 검증, 남은 한계를 짧게 덧붙이며 전체 코드의 무결성이나 사용자 성과까지 보장하지 않는다.
