# 선택권에 대한 개념
하나의 방향으로 코드를 선택하면 그 선택에 따라 다음 코드들이 어느정도는 결정되게 된다.
이 선택에 따른 비용이 든다는 것이다. 이 비용이 높아지게 되면 소프트웨어의 future가 제한된다. 
이를 막기위해서는 기능구현 사이에 코드를 관찰하고 발전시켜서 future를 고려한 작업이 사이사이에 들어가야한다.

# 판단기준스킬

- 통합 [코드베이스 설계](../codebase-design/SKILL.md)를 실제 변경과 관련 호출부에 대조한다. 변경과 보존 대상, 책임과 지식의 위치, 공개 계약과 외부 형식, 상태·오류의 의미, 호출자·데이터 이행과 검증 근거를 관련 범위에서 확인한다.

## 추가적인 기준들

- 너무 많은 기능을 한 번에 구현하여 향후 유지보수 비용이 증가하는 경우
- 특정 기술 스택이나 라이브러리에 의존하여 향후 변경이 어려워지는 경우
- 코드 구조가 복잡하여 새로운 기능 추가나 변경이 어려워지는 경우
- 설계가 유연하지 않아 미래의 요구사항에 대응하기 어려운 경우
- 하나의 파일이나 함수에 너무 많은 책임이 집중되어 있어 향후 변경이 어려워지는 경우

## 참고한 발표와 이 스킬의 적용

Kent Beck의 *Software Engineering in the Age of AI*, Prodacity 2026을 참고했다. [참고한 영상](https://www.youtube.com/watch?v=F8fBgDCf2Y4&t=1s)과 [게시자 Rise8의 발표 전문](https://www.rise8.us/videos/kent-beck-software-engineering-in-the-age-of-ai)이 출처다.

발표는 effort·output·outcome·mission을 구별하고, 쉽게 세는 지표가 목적을 대신할 때의 왜곡을 짚는다. 미션은 측정과 기여 귀속이 어렵고 위기에서 가치가 드러나기도 한다. 기능 제공과 미래 변경의 선택권 사이에서 지연 비용을 고려하며, 사용 피드백과 학습으로 설계를 갱신한다.


## 범위와 근거 확인

사용자가 지정한 diff, PR, 파일 또는 기능을 대상으로 삼는다. 변경 리뷰라면 기준 버전과 diff를 확인하고, 기존 코드 리뷰라면 지정한 기능의 호출 경로를 확인한다. 범위가 불명확해 결론이 달라질 때만 필요한 범위를 확인한다.

목적과 실제 사용 상황을 기존 요청·문서·코드에서 파악한다. 사용자에게 없는 목적이나 우선순위를 만들지 않는다. 변경 줄만 보지 말고 관련 호출부, 입력과 출력, 데이터 흐름, 상태 갱신, 오류 처리와 기존 검증을 필요한 만큼 읽는다. 변경에서 발견한 기존 문제는 이번 변경이 만든 문제와 구분하고 범위 밖 조사를 무제한으로 넓히지 않는다.

리뷰 요청 자체로 수정·커밋·배포 권한을 얻지 않는다. 읽기 조사와 허용된 검증으로 판단하며, 이미 별도로 받은 수정 권한은 그 범위 안에서 유지한다.

## 판단할 것

### 지금 쓰는 데 걸리는 문제

누가 어떤 입력이나 동작을 했을 때 무엇을 할 수 없거나 잘못 판단하게 되는지 확인한다. 기대한 결과와 실제 코드가 만드는 결과 사이의 차이를 설명한다. 정확성, 오류 복구, 데이터 보존, 응답성 등은 해당 사용 흐름에 영향을 줄 때 살핀다.

가능하면 실제 호출 인터페이스나 사용자 흐름으로 재현한다. 실행하기 어렵다면 문제를 만드는 분기·값·호출 순서를 코드로 추적한다. 정적 분석으로 확인한 문제와 실행으로 관찰한 결과를 구별한다. 빌드 성공이나 테스트 존재만으로 사용 동작이 검증됐다고 판단하지 않는다.
  
미래 요구의 근거가 없으면 만들어 지적하지 않는다. 코드에서 이미 드러나는 지식 분산이나 숨은 사용 조건은 어떤 구체적인 변경에서 비용을 만드는지 설명할 수 있다. 그 변경이 확정된 계획인지 판단을 위한 예시인지 밝힌다. 짧게 쓰고 버릴 기능과 오래 운영할 기능에 같은 구조 투자를 요구하지 않는다. 현재 제약을 받아들일 이유가 충분하면 그 선택을 결함으로 보고하지 않는다.
