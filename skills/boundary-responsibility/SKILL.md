# 경계와 책임 분리

한 가지 변경에 필요한 지식이 담당 모듈에 모이도록 작성한다. 호출자는 적은 지식으로 기능을 사용하고, 내부 구현이 바뀌어도 관련 없는 호출부는 그대로 사용할 수 있어야 한다. 하나의 함수 하나의 파일안에 너무많은 책임을 넣지 않도록 한다.

이 스킬은 코드 설계와 검토 기준이다. 기존 프로젝트 구조와 요청 범위 안에서 적용하며, 별도 계층이나 프레임워크 도입을 전제하지 않는다.

## 수정 전에 확인할 것
기존 모듈을 확장하기 전에, 그 모듈에 함께 있는 책임들의 변경 이유를 확인한다. 독립적으로 바뀌는 정책이 묶여 있다면 분리 여부를 판단한다. 보조 기능 하나를 쓰려고 관련 없는 기능 전체를 의존하는 호출부도 확인한다.

실제 데이터 흐름과 호출부를 읽고 다음을 정한다. 작은 수정이면 해당 위치와 영향을 확인하는 것으로 충분하다. 복잡한 작업이면 짧은 표나 메모로 남긴다.

- 무엇이 바뀌는가? 표시 이름 변경, 외부 응답 변경, 조회 정책 변경처럼 구체적인 상황을 사용한다.
- 그 변경을 책임질 모듈은 어디인가? 해당 판단과 정보를 한곳에서 수정할 수 있는지 확인한다.
- 데이터와 상태의 주인은 누구인가? 생성·검증·변경을 담당하는 곳과 읽기만 하는 곳을 구분한다.
- 호출자가 알아야 할 입력·결과·오류는 무엇인가? 호출 순서나 설정 등 숨은 사용 조건도 포함한다.

신규 기능이나 여러 책임을 바꾸는 작업은 코드 작성 전에 위 네 항목을 짧은 책임·소유권 표나 항목으로 기록한다. 각 행은 독립적인 변경 이유, 담당 모듈, 원본 상태의 소유자와 갱신 경로, 호출자가 알아야 할 계약을 연결한다. 한 줄 수정은 기존 담당과 영향을 확인하는 것으로 충분하다. 사용자의 실제 요구와 현재 코드에 근거하며, 모든 앱을 다중 사용자 서비스로 가정하지 않는다.

기존 책임이 명확하면 재사용한다. 파일 길이나 폴더 이름만으로 책임을 추측하지 않는다. 적용되는 설계 통과 조건을 메인의 완료 기준에 포함하고, 파일 분리 여부나 줄 수로 대신하지 않는다.

## 작성 기준

### 같은 지식을 한곳에서 관리한다

- 여러 호출부가 같은 공급자 이름, 응답 필드, 상태 규칙을 각각 해석하면 담당 모듈로 모은다.
- 함께 바뀌는 정보는 같은 정의를 참조한다. 서로 독립적으로 바뀌는 정책은 구분한다.
- 모양이 비슷하다는 이유만으로 다른 도메인의 규칙까지 하나로 합치지 않는다.

### 외부 형식은 경계에서 내부 모델로 바꾼다

- 네트워크, 저장소, 프로세스 간 통신 등 신뢰 수준이 바뀌는 입력을 검증한다.
- 외부 필드명, 인증·서명 방식, 공급자별 예외 처리는 연동 담당 안에 둔다.
- 공통 화면과 계산은 내부 모델을 사용한다. 같은 데이터에 대한 형식 추측과 검증을 호출부마다 반복하지 않는다.
- 정규화 과정에서 의미를 잃지 않는다. 수량의 단위, 조회 시점, 부분 성공처럼 사용자가 판단하는 데 필요한 차이는 모델에 보존한다.

### 데이터와 상태의 소유권을 정한다

- 하나의 사실을 여러 곳에서 독립적으로 갱신하지 않는다. 원본 상태와 그 상태를 바꾸는 담당을 정한다.
- 원본에서 계산 가능한 필터 결과와 집계는 우선 계산으로 표현한다. 캐시가 필요하면 무효화 책임도 정한다.
- 조회 담당은 로딩·성공·실패 전이를 관리하고, 연동 담당은 외부 조회를 수행하도록 구분한다. 기존 구조에서 더 단순한 구성이 가능하면 그것을 따른다.
- 비동기 결과가 겹치는 경우 최신 요청 판정, 취소, 중복 실행 정책의 담당을 정한다. 필요가 확인되지 않은 상태 관리 계층은 만들지 않는다.

### 호출자가 배워야 할 것을 줄인다

- 필요한 입력과 결과만 노출하고 공급자별 플래그와 실행 순서는 담당 모듈 내부에서 처리한다.
- 오류를 삼키거나 빈 성공 결과로 바꾸지 않는다. 전체 실패와 부분 실패는 호출자가 필요한 수준으로 구분해 전달한다.
- 단순 전달 함수나 범용 인터페이스를 추가하기 전에 호출자의 지식이나 반복 코드가 실제로 줄어드는지 확인한다.
- 등록 목록이 실제 확장 지점이면 기준이 되는 ID 목록에서 타입을 유도하고 누락된 연결을 검사한다. 정적 타입을 쓰기 어려운 환경에서는 시작 시 검증 등 해당 환경의 수단을 사용한다.

### 분리 비용도 확인한다

- 줄 수나 함수 수를 목표로 나누지 않는다. 함께 읽어야 이해되는 작은 코드는 함께 둔다.
- 검색 규칙, 표 표시, 공급자 연동 등이 독립적으로 변하기 시작하면 그 책임을 분리한다.
- 추측한 미래 공급자를 위해 플러그인 시스템, 공통 기반 클래스, 불필요한 의존성 주입 구조를 만들지 않는다.
- 인터페이스를 변경할 때는 실제 호출부도 함께 바꾼다. 요청과 무관한 구조 정리는 확대하지 않는다.


## 완료 전 검토와 검증

변경한 코드와 호출부를 구현 전 책임·소유권 기록과 대조하고 다음을 확인한다. 배치가 바뀌었으면 실제 소유자와 변경 이유를 갱신하되, 원래 통과 조건을 구현에 맞춰 낮추지 않는다.

- 한 가지 변경을 가정했을 때 수정 위치가 해당 담당에 모이는가?
- 공통 호출부에 외부 응답 해석이나 공급자별 분기가 새로 퍼지지 않았는가?
- 데이터와 상태를 누가 갱신하는지 추적할 수 있는가?
- 분리 후 호출자가 알아야 할 조건과 파일 간 왕복이 줄었는가?
- 새 등록 항목이나 오류 상태를 빠뜨렸을 때 발견할 수 있는가?

영향받는 동작을 실제 호출 인터페이스나 사용자 흐름으로 검증한다. 공통 경로를 바꾸었다면 서로 다른 공급자 구현에도 같은 계약이 유지되는지 확인한다. 실패·부분 성공·동시 조회는 변경과 관련 있을 때 확인한다. 기존 검사를 활용하고, 검증이 필요한 동작에 맞춰 테스트를 추가한다.

문제를 일부 보완했어도 원래 지적한 책임·호출부·상태 갱신의 전체 범위를 다시 확인하기 전에는 해결로 닫지 않는다. 결과에는 실제 책임과 소유자, 확인한 코드·호출부 위치, 어떤 변경을 그곳에서 처리할 수 있게 됐는지 설명한다. 실행한 검증과 확인하지 못한 동작을 구분한다. 빌드 성공만으로 실제 동작을 검증했다고 보고하지 않는다.
