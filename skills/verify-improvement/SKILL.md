# 플러그인 개선 검증

같은 요청에서 변경본의 개선과 회귀를 확인한다. 전체 책임 경계는 [스킬 기능과 책임](../../skill-refer.md)를 따른다.

## 검증 대상과 역할

사용자가 받는 동작, 스킬 호출·선택 방식, 책임 경계 또는 기능을 바꾸는 변경을 비교한다. 새 스킬은 새 동작을 추가하므로 비교한다. 오타·링크·표현만 수정해 사용자 작업과 결과가 그대로면 이 스킬을 사용하지 말고 형식·참조·변경 내역과 기능 문서의 일치를 확인한다. 사례 수와 범위는 영향에 맞춘다. 공통 변경 절차는 [스킬 기능과 책임](../../skill-refer.md#공통-변경-절차)를 따른다.

변경 담당자는 사용자 요구, 동일한 요청·입력, 사전 관찰 기준, 허용 범위, 요청 당시 작업폴더, 기준본과 `change` 변경본의 커밋 식별자를 제공한다. 기준본은 변경 출발 커밋이다. 미커밋 원본 변경을 복사하거나 검증용 작업 트리의 시험 대상 지침을 수정하지 않는다. 변경본 커밋이 준비되지 않았으면 작성 담당자에게 반환한다. 검증 후 내용이 바뀌면 새 커밋으로 다시 시작한다.

바뀐 규칙이나 판단마다 시험 입력의 조건, 관찰할 행동과 관련 회귀 위험을 연결해 사례를 고른다. 판단 자체를 검증하는 시험에서는 요청이 그 선택을 미리 지시했는지 확인한다. 명시적으로 위임을 요청한 시험의 수행 근거와 상황에 따라 위임 필요성을 스스로 판단한 근거를 구분한다.

메인 검증 담당이 두 버전의 작업 트리와 플러그인 적용 상태를 직접 만들고 관리한다. 각 버전 실행은 대화 이력을 상속하지 않는 별도 서브에이전트가 맡는다. 실행 담당자마다 아래 인계 항목을 동일하게 맞추고 해당 버전만 적용한다. 상대 실행 결과, 작성자 주장, 승자를 암시하는 설명은 전달하지 않는다. 스킬 파일을 직접 읽혀 실행한 결과는 자동 선택 검증으로 간주하지 않는다.

각 실행 담당자에게 전달할 것:

- 정확한 요청과 입력 자료, 시험 대상 작업 및 검증할 행동 가설
- 해당 작업 트리 경로와 버전 식별자, 마켓플레이스·프로젝트 설정·캐시 확인 근거
- 모델, 도구와 권한, 시작 상태
- 허용·금지 행동, 기대 산출물과 기록할 증거

각 실행 담당자는 결과와 수행에 필요한 증거만 반환한다. 메인은 양쪽 조건이 실제로 같았는지 기록한다.

실행이 끝나면 메인 담당은 버전을 드러내는 표식과 경로를 제거해 산출물 및 필요한 실행 근거를 A/B로 익명화한다. 별도의 블라인드 평가 서브에이전트에는 아래 항목만 전달한다. 평가자는 어떤 결과가 기존본 또는 변경본인지, 작성자가 원하는 승자가 무엇인지 알 수 없어야 한다. 변경 작성자의 주장이나 추천은 전달하지 않는다. 평가자는 결과와 근거만 반환한다. 버전 대응을 가린 직후에도 후보를 추론할 단서가 남거나 역할 분리가 불가능하면 그 한계를 기록하고 판단 불가로 처리한다.

평가 담당자에게 전달할 것:

- 사용자 작업과 수용 기준
- 버전 식별정보를 드러내지 않게 정리한, 결과 해석에 영향을 주는 실행 환경 차이
- 사전에 고정한 평가 기준과 [평가 지침](references/evaluation-agent.md)
- 익명화된 A/B 결과와 관련 실행 증거

메인은 사용자 요구·시험 작업·관찰 기준과 각 실행에 필요한 맥락을 먼저 구성해 실행 담당자들에게 전달한다. 별도 평가 서브에이전트는 고정 등록 에이전트가 아니라 이 스킬의 [평가 지침](references/evaluation-agent.md)을 전달받는 역할이다. 평가가 끝난 뒤 메인은 버전 대응을 공개하고 A/B 판정을 기준본·변경본에 대응시켜 변경본이 우세하면 `개선`, 기준본이 우세하면 `회귀`, 동률이면 `차이 없음`으로 정리한다. 후속 작업은 변경 담당자가 공통 변경 절차의 판정 규칙에 따라 수행한다.

## 버전 격리와 실행

1. 메인 검증 담당이 요청 당시 작업폴더 아래 이번 실행만의 두 경로를 정한다. 원본 저장소에서 `git worktree add --detach <기존본 경로> <기준 커밋>`과 `git worktree add --detach <변경본 경로> <change 커밋>`으로 각각 고정한다. 작업 트리만 나눈다고 플러그인 버전이 격리되는 것은 아니다.
2. 각 작업 트리를 루트로 별도 이름의 로컬 마켓플레이스를 준비한다. 카탈로그 `.agents/plugins/marketplace.json`의 로컬 소스 경로는 자기 작업 트리의 플러그인 루트를 가리켜야 한다. 루트에 플러그인 등록 정보와 스킬 폴더가 있는 이 저장소는 `source: {"source": "local", "path": "./"}`를 사용할 수 있으며 `plugins/<name>`으로 복제할 필요가 없다. 시험용 카탈로그는 검증 커밋과 구분해 기록한다.
3. 코덱스 명령줄 도구에서 각 로컬 마켓플레이스를 등록하고 플러그인을 설치한다. 예: `codex plugin marketplace add <marketplace-root>` 다음 `codex plugin add <plugin>@<marketplace>`. 각 프로젝트의 `.codex/config.toml`에서는 해당 실행에 쓸 마켓플레이스의 플러그인만 활성화하고 다른 버전은 비활성화한다. 예: `[plugins."<plugin>@<marketplace>"]` 아래 `enabled = true`를 두고 비교 대상이 아닌 항목은 `enabled = false`로 둔다.
4. 실행 전에 마켓플레이스 카탈로그의 이름과 `source.path`, 실제 플러그인 경로, 프로젝트별 활성화 설정, `codex plugin list` 결과와 설치 캐시 경로를 대조한다. 캐시 안에 해당 플러그인의 `plugin.json`과 시험 대상 `SKILL.md`가 있는지도 확인한다. 설치 명령줄 도구와 실행 에이전트의 계정·`CODEX_HOME`이 같은 설정과 캐시를 참조하는지도 확인한다. 캐시 파일만 존재하는 것으로 활성 설치나 런타임 검색을 확인했다고 보지 않는다.
5. 새 코덱스 명령줄 도구 대화에서 각 버전을 따로 실행한다. 실행 중 로드된 버전이 의도한 대상인지 확인할 수 없거나, 두 플러그인이 함께 활성화되거나, 스킬이 검색·사용 가능한지 확인할 수 없으면 행동 비교를 중단하고 판단 불가로 반환한다. 런타임 확인을 위해 전역 사용자 설정이나 기존 설치를 임의로 변경하지 않는다.
6. 결과를 보기 전에 사전 관찰 기준을 고정한다. 핵심 요구를 대표하는 사례와 관련 회귀 사례를 포함하고, 자동 선택 변경은 발동 및 비발동 사례를 모두 둔다. 두 버전 모두 같은 요청을 수행하며, 새 스킬이 없는 기존본도 동일한 요청을 받는다.

등록 정보, 문서 머리말, 이름·경로, `skill-refer.md`와 지침의 일치, 변경 내역 및 사용 가능한 검사기 결과도 확인하되, 구조 검사는 행동 비교를 대신하지 않는다. 시험 중 실제 원격 원격 반영·변경 검토 요청 생성·병합·설치 업데이트는 하지 않는다. 회고와 개선이나 플러그인 변경 제출 자체를 시험하더라도 재귀적인 수정·제출을 시작하지 않는다.

## 시험 환경 정리

설정 전에 이번 실행이 만들 작업 트리의 정확한 경로, 플러그인 식별자와 마켓플레이스 이름, 설치·캐시 경로, 기존 마켓플레이스 등록 및 플러그인 설정을 기록한다. 실행과 평가가 끝나면 결과·로그·필요한 증거를 작업 트리 밖에 보존한 뒤 정리한다. 판단 불가나 실행 실패여도 가능한 정리를 수행한다.

이번 실행에서 설치한 플러그인만 `codex plugin remove <plugin>@<marketplace>`로 제거하고, 이번 실행에서 등록한 마켓플레이스만 `codex plugin marketplace remove <name>`으로 제거한다. 프로젝트 임시 설정과 설치·캐시 항목이 사라졌는지 확인하고, 기록한 개인용·기존 플러그인 설정이 그대로인지 대조한다. 예상 밖의 차이가 있으면 기존 설정을 덮어쓰지 말고 정리를 중단해 메인 담당자에게 보고한다.

이번 실행에서 만든 작업 트리만 정리한다. 제거 전 `git status --porcelain`을 확인하고, 알려진 시험용 파일만 제거해 상태가 깨끗할 때 일반 `git worktree remove <path>`를 사용한다. `--force`나 재귀 삭제는 금지한다. 알 수 없는 수정·미추적 파일이 남으면 해당 작업 트리의 경로와 정확한 상태를 보존·보고하고 메인 담당자가 수동 처리하게 한다. 제거 뒤 `git worktree list`와 디스크에서 경로가 사라졌는지 확인한다. 검증 담당자는 원본의 `change`를 삭제하지 않는다. 원본 브랜치 정리는 변경·제출 담당자의 책임이며 변경 검토 요청의 원격 변경 브랜치와 구분한다.

## 판정과 반환

블라인드 평가자는 관찰 기준과 사용자 요구에 따라 `A 우세`, `B 우세`, `차이 없음`, `판단 불가` 중 하나와 근거를 반환한다. 변경본을 모르는 평가자는 `개선`이나 `회귀`를 판정하지 않는다. 메인은 버전 대응을 공개한 뒤 이 판정을 기준본·변경본에 연결해 최종 분류한다. 승자를 반드시 고르지 않으며, 일부 사례의 개선이나 단일 비교를 일반적인 성능 향상으로 확대하지 않는다.

변경 담당자는 개선이면 제출, 회귀·차이 없음이면 이번 `change` 폐기, 판단 불가·실패면 보존하는 공통 절차를 적용한다. 평가자는 수정·채택·되돌림·변경 검토 요청 여부를 결정하거나 수행하지 않는다. 검증 담당은 요청·입력·관찰 기준, 익명 결과, 실행 기록, 버전 식별자와 해시, 환경, 재현 방법, 검사 결과, 한계, 판정과 검증 작업 트리 경로·상태를 반환한다.

재시도가 필요한 수정은 변경 담당자가 원본 `change`에서 새 커밋으로 수행하고 다시 검증한다. 판단 불가를 회귀나 차이 없음으로 취급하지 않는다. 타인의 파일을 포함한 정리나 강제 작업 트리 삭제는 하지 않는다.
