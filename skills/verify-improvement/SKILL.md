# 플러그인 개선 검증

목표는 변경본이 같은 작업에서 기존본보다 나아졌는지 확인하는 것이다. 문서가 정돈됐거나 형식 검사를 통과한 것만으로 개선이라고 판단하지 않는다. 이 스킬은 검증을 담당하며 제품 변경과 PR 제출은 작업 담당자에게 돌려준다.

## 입력과 담당

작업 담당자는 소스 저장소, 기존본과 변경본의 고정된 식별자, 변경 파일 목록, 사용자가 요구한 동작, 재현용 자료, 허용된 작업 범위를 준비한다. 기본 소스는 `D:\Plugin\namuk-process`이다. 기존본은 이번 변경의 출발 커밋을 사용하며 실행 중 움직이는 브랜치 이름만 기록하지 않는다. 설치본과의 비교를 요청받았다면 실제 설치 버전과 소스의 대응을 확인한다. 대응을 확인하지 못하면 설치본 비교라고 부르지 않는다.

변경본에 미커밋·미추적 파일이 있으면 제출 대상만 별도 스냅샷으로 보존하고 파일 목록과 해시를 기록한다. 검증 중 담당자는 이 스냅샷을 바꾸지 않는다. 검증 후 제출 대상 내용이 달라지면 기존 결과를 재사용하지 않는다.

검증 담당은 반드시 새 서브에이전트로 생성하고 `fork_turns="none"`으로 대화 이력 상속을 끈다. 이 스킬 경로와 고정된 두 버전, 실제 사용자 요구·자료·작업 제한만 전달한다. 작성자의 설명, 선호하는 수정안, 성공 주장, 이전 평가 결론은 전달하지 않는다. 검증 담당으로 이미 생성됐다면 이 스킬을 다시 위임하지 않는다.

서브에이전트를 만들 수 없거나 맥락 분리를 보장할 수 없으면 독립 검증 불가로 반환한다. 작성자의 자체 평가로 대체해 통과시키지 않는다.

## 검증 환경과 비교

1. 저장소 신원과 버전 식별자를 확인하고, 검증 담당만 쓰는 별도 Git worktree 하나를 만든다. 작업 담당자의 worktree와 설치 캐시는 수정하지 않는다. 모든 명령에 검증 경로를 명시한다. 변경본의 수정·삭제·미추적 파일을 포함해 정확한 버전을 재현한다.
2. 두 버전의 결과를 보기 전에 같은 테스트 요청과 관찰 기준을 정한다. 사용자 요구를 대표하는 최소 사례와 변경 관련 회귀 사례를 고른다. 예를 들어 자동 실행 범위를 바꿨다면 실행할 상황과 실행하지 않을 상황을 확인한다. 문구만 바꿨다면 해당 의미의 해석을 비교하는 작은 사례로 충분하다. 기준은 특정 문장 일치보다 실제 행동·산출물로 판단한다.
3. 기존본을 검증 worktree에 준비하고 새 실행 에이전트를 `fork_turns="none"`으로 만든다. 해당 버전의 플러그인, 테스트 요청, 입력 자료와 작업 제한만 준다. 정답·평가 기준·변경 내역은 주지 않는다. 역할은 테스트 요청 수행이며 검증 스킬 재실행이 아니다.
4. 기존본 실행이 끝나면 실제 행동·도구 실행·산출물을 검증 worktree 밖의 결과 디렉터리에 보존한다. 검증 담당이 만든 파일만 정리하고 입력 상태를 복구한 뒤 같은 worktree에 변경본을 준비한다. 다른 새 실행 에이전트에게 같은 요청을 준다. 기존본의 대화·산출물·평가를 노출하지 않는다. 두 실행은 순차 진행하며 모델·도구·권한·입력 조건을 맞춘다.
5. 각 실행에는 시험하는 버전의 플러그인만 적용한다. 이미 설치된 Namuk Process 지침이 함께 적용되는지 확인한다. worktree를 만들었다는 이유만으로 플러그인 격리가 됐다고 가정하지 않는다. 격리가 불가능하면 비교 불가로 기록한다. 스킬 파일을 명시적으로 읽힌 시험은 동작 시험이며 자동 선택 검증으로 보고하지 않는다.
6. 변경본의 manifest, 스킬 frontmatter·참조 경로와 diff를 검사하고 사용 가능한 validator 및 `git diff --check`를 실행한다. 검증기 부재나 실패는 결과에 남긴다. 구조 검사는 행동 비교와 구분한다.

시험 중 실제 원격 push·PR 생성·병합·설치 업데이트는 하지 않는다. 필요하면 로컬 시험 저장소나 기록용 대체 도구로 전송 직전의 동작을 확인하고 실제 전송은 미검증으로 남긴다. 시험 대상이 reflect·submit-improvement라도 시험 제한이 우선하며 실제 제출이나 재귀적 개선 작업을 시작하지 않는다.

## 결과와 후속 작업

각 사례의 입력·관찰 기준·기존 결과·변경 결과·실행 기록·산출물 위치를 남긴다. 버전 식별자, 스냅샷 해시, 환경, 재현 방법, 구조 검사 결과와 한계도 기록한다. 결론은 `개선 확인`, `차이 없음`, `회귀 발견`, `판단 불가`로 구분한다. 일부 사례만 좋아졌다면 그 범위를 적고 중요한 회귀를 숨기지 않는다. 한 번의 비교로 일반적인 성능 향상을 주장하지 않는다.

검증 담당은 결과와 구체적인 추가 개선 여지를 작업 담당자에게 반환하고 직접 소스를 고치거나 PR을 보내지 않는다. 작업 담당자는 개선이 확인되면 [submit-improvement](../submit-improvement/SKILL.md)에 변경과 검증 보고서를 넘긴다. 독립적으로 호출된 검증도 원래 호출자가 이 후속 작업을 맡는다.

추가 수정이 필요하면 작업 담당자가 근거 있는 최소 수정을 하고 새 스냅샷을 다시 검증한다. 자동 수정·재검증은 한 차례까지 수행한다. 여전히 회귀하거나 판단할 수 없으면 멈추고 해당 결과를 알린다. 사용자가 미검증 초안 제출을 요청한 경우에만 한계를 명시해 submit-improvement로 넘긴다. 차이가 없으면 개선을 주장하지 않으며, 기능·문서 추가 등 별도 변경 목적이 충족됐는지에 따라 제출한다. 검증만 요청된 작업에서는 제출하지 않는다.

PR에 필요한 증거를 보존하고 검증 worktree의 경로와 상태를 반환한다. 타인의 파일을 포함한 정리나 강제 삭제는 하지 않는다.
