# 플러그인 변경 제출

이 스킬은 준비된 플러그인 변경의 제출을 담당한다. 변경은 사용자의 직접 작업, 기능 구현, 버그 수정, 문서·설정 정리, 회고와 개선 등에서 올 수 있다. 회고와 개선 실행이나 회고 결과를 필수 조건으로 요구하지 않는다. 소스 수정과 기본 검사는 변경 담당자가, 사용자 요청이 있는 비교검증은 플러그인 개선 검증이 담당한다. [공통 검사·비교 정책](../../skill-refer.md#검증-수준과-역할-분리)을 따른다. 사용자가 보고만 요청하거나 전송 범위를 제한하면 그 범위를 따른다.

## 실행 담당

메인 또는 변경 담당자가 호출하면 별도 서브에이전트 하나에 제출을 맡긴다. 소스·작업 트리 경로, 원격 저장소, 대상 브랜치와 변경 브랜치, 제출할 파일·커밋, 변경 목적과 배경, 기본 검사 기록·비교 수행 상태·미확인 항목, 사용자 제한을 전달한다. 이미 제출 담당자로 위임받았다면 다시 위임하지 않는다. 회고와 개선을 다시 호출하지 않는다.

제출 담당자는 스킬 기능과 책임 문서에 지정된 로컬 원본에서 수정·기본 검사를 마친 변경을 받아 같은 저장소의 `change` 브랜치에서 제출 대상 커밋의 원격 반영·변경 검토 요청 제출을 수행한다. 별도 제출용 작업 트리로 옮기는 것을 기본 절차로 삼지 않는다. 제출 중에는 담당자만 해당 작업 트리와 브랜치에 쓰며 메인과 다른 담당자는 동시에 수정하지 않는다. 타인의 변경을 되돌리지 않고 미커밋·미추적 파일도 제출 범위와 구분한다. 구분할 수 없으면 임의로 수정할 파일로 등록하지 않는다. 모든 깃 명령은 로컬 원본 경로를 명시해 실행한다.

완료 시 변경 요약, 작업 트리·브랜치, 기본 검사·비교 수행 상태와 한계, 확인된 변경 검토 요청 주소를 메인에 반환한다. 막히면 완료 단계와 장애를 반환한다. 메인은 결과를 회수해 사용자에게 전달한다. 서브에이전트를 사용할 수 없으면 제한을 알리고 메인이 같은 절차를 수행한다.

## 제출할 변경 확인

로컬 원본 경로, 원격 저장소, 로컬 `change`와 원격 변경 브랜치, 대상 브랜치 `main`, 변경 파일 목록, 변경 목적과 이유, 기본 검사 기록·비교 요청 및 수행 상태·미확인 항목을 확인한다. 직접 호출된 경우 현재 대화와 원본의 깃 상태에서 같은 정보를 확인한다. 전달받은 경로가 스킬 기능과 책임 문서의 원본과 일치하는지 확인하며, 검증용 작업 트리를 제출 원본으로 대신 사용하지 않는다. 변경이 없으면 빈 변경 검토 요청을 만들지 않고, 아이디어만 있다면 먼저 원본 수정·기본 검사가 필요함을 알린다. 기본 검사 기록이 없으면 변경 담당자에게 기본 검사를 요청한다. 비교 미요청을 이유로 비교 단계에 되돌리거나 제출을 막지 않는다.

대상 브랜치는 `main`, 로컬 변경 브랜치는 수정 전에 준비한 `change`다. 다른 브랜치에서 변경했거나 브랜치가 없으면 제출 시 새 이름을 만들지 말고 변경 담당자에게 반환한다. 원격 기준을 조회하고 `main` 대비 전체 변경 내역·커밋에 무관한 변경이 없는지 확인한다. 원격 조회 실패를 숨기거나 원본을 원격 상태로 덮어쓰지 않는다. 기록의 대상 커밋과 현재 `change`가 다르면 변경 담당자가 기본 검사 기록을 갱신하고, 요청된 비교 기록도 현재 변경에 맞는지 확인한다. 기준 갱신·충돌 해결은 변경 담당자가 수행한다.

원격 변경 브랜치는 `change/<주제>-<고유값>`으로 정해 로컬 고정 이름과 분리한다. 동일 작업 재시도에는 기록한 원격 변경 브랜치와 변경 검토 요청을 재사용하며, 다른 열린 변경 검토 요청의 변경 브랜치를 덮어쓰지 않는다. 원격에 `change`라는 브랜치가 있어 하위 이름을 만들 수 없으면 그 브랜치를 삭제하지 않고 충돌을 보고한다. 원격 변경 브랜치는 열린 변경 검토 요청 보존에 필요하므로 로컬 `change` 정리와 함께 삭제하지 않는다.

작업 경로가 남욱 프로세스 소스의 깃 작업 트리인지, 등록 정보의 이름이 `namuk-process`이고 `origin`이 `skadnr3126/namuk-process`인지 확인한다. 설치본·캐시에서는 실행하지 않는다. 이번 변경과 사용자 기존 변경을 구분할 수 없으면 임의로 묶어 커밋하지 않는다.

## 변경 검토 요청 제출과 사후 검토

모든 제출에는 기본 검사 기록과 정확한 대상 커밋을 요구한다. 비교 미요청이면 기본 검사만으로 제출한다. 사용자가 비교를 요청한 경우에는 [플러그인 개선 검증](../verify-improvement/SKILL.md)의 해당 커밋 개선 판정을 요구하며, 회귀·차이 없음·판단 불가·실패는 공통 후속 규칙을 따른다. 필요한 기록이 없거나 현재 변경과 맞지 않으면 변경 담당자에게 해당 검사·비교 기록을 요청한다. 사용자 범위 제한은 우선한다.

변경 내역에서 범위와 민감정보를 확인하고 `git diff --check`를 실행한다. 제출 대상은 이미 커밋되고 검사 기록이 있어야 하므로 제출 단계에서 내용을 추가하거나 검사하지 않은 파일을 등록하지 않는다. `git push origin change:refs/heads/<원격 head>`로 제출 커밋을 올린다. 기존 변경 검토 요청이 있다면 대상 브랜치·변경 브랜치를 확인해 재사용하고, 없으면 `main` 대상 초안 변경 검토 요청을 만든다. 별도 수정안 승인 단계는 두지 않으며 실행 환경의 권한 요청만 해당 작업에 한해 수행한다.

변경 검토 요청만 읽어도 판단하도록 다음 내용을 남긴다.

- 목적과 배경: 어떤 요청이나 필요로 변경했는지. 버그 수정이면 증상과 재현 조건, 기능 추가면 사용 목적, 회고와 개선에서 왔다면 피드백과 관찰 결과를 적는다. 대화 전문 대신 필요한 맥락만 익명화한다.
- 변경: 무엇을 추가·수정·삭제했고 다음에는 어떤 행동이 달라지는지.
- 검사·비교: 수행한 기본 검사와 근거·대상 커밋, 비교 요청 여부와 수행 상태를 적는다. 비교 미실행이면 `동작 비교 미실행 / 기본 검사만 수행`과 한계를 명시한다. 실제 비교를 수행했다면 요청·예상 및 실제 결과·재현 방법·각 소스 기준을 적는다.
- 한계: 실행하지 못한 검사, 남은 불확실성, 사용자가 검토할 판단.

깃허브 명령줄 도구 사용 시 변경 검토 요청 본문을 UTF-8 파일로 쓰고 `gh pr create --draft --base <대상 브랜치> --head <원격 head> --title <제목> --body-file <파일>`로 제출한다. 변경 검토 요청 주소와 대상 브랜치를 조회해 제출을 확인한다. 원격 반영 성공만으로 변경 검토 요청을 만들었다고 보고하지 않는다.

원격 변경 브랜치의 커밋과 변경 검토 요청의 대상 브랜치·변경 브랜치·주소를 확인한 뒤 원본에서 `main`으로 복귀한다. 변경 검토 요청 제출이 성공해도 로컬 `change`는 삭제하지 않는다. 미제출 작업이 남아 있을 수 있으므로 브랜치를 보존한다. 원본 작업 트리와 열린 변경 검토 요청의 원격 변경 브랜치도 보존한다. 원격 반영·변경 검토 요청 확인 실패 또는 예상 밖 미커밋 변경이 있으면 강제로 진행하지 않고 상태와 장애를 보고한다. 검증 작업 트리와 시험용 설치 정리는 플러그인 개선 검증이 맡는다.

채팅에는 변경 요약, 기본 검사·비교 수행 상태, 변경 검토 요청 링크만 짧게 알린다. 제출이 막히면 완료·실패한 단계와 로컬 변경 위치를 알리고 재시도 시 기존 브랜치·변경 검토 요청을 확인한다. 자동 병합이나 설치본 업데이트는 하지 않는다. 사용자가 검토·병합한 뒤 업데이트를 요청하면 별도로 진행한다.
