# 요청 검증 기준

다음 행동을 정할 정보가 충분한지, 요청의 전제에 대한 맥락이 있고, 요청의 전제가 실제 맥락과 맞는지, 요청한 작업이 원하는 결과에 연결되는지 판단한다. 전체 실행 순서와 위임은 [요청 검증과 구현 위임](../request-to-implementation/SKILL.md)이 소유한다. 이 스킬은 불확실한 부분의 판단 기준을 제공하며 검증 항목마다 별도 담당자를 만들지 않는다.

## 공통 판단 원칙

대화와 이미 확보한 근거를 재사용한다. 사용자 요구와 경험, 조사로 확인한 사실, 메인의 해석·가정·예상을 구분한다. 요청 문장의 길이나 형식, 정돈된 명세의 존재만으로 이해 여부를 판단하지 않는다.

조사로 알아낼 사실은 직접 확인한다. 사용자만 정할 정보가 부족해 사용자 경험·작업 범위·제약·완료 기준을 결정할 수 없거나 답에 따라 이들이 달라질 때 질문한다. 확정된 요구와 제약 안에서 구현 세부사항은 담당자가 판단한다. 이미 답한 질문을 반복하거나 파일명·구현 방법을 사용자에게 요구하지 않는다. 답을 기다리는 동안 해당 결정에 의존하는 실행만 보류하고 독립적인 조사는 계속한다.

질문에는 현재 이해와 근거, 남은 결정, 선택에 따른 결과 차이를 짧게 담는다. 선택지를 제안하더라도 사용자 답을 그 안으로 제한하지 않는다.

작은 변경은 관련된 기존 맥락으로 판단한다. 맥락이 적은 새 설계나 큰 구조 변경은 영향을 받는 범위까지 확인한다. 설계 초안을 만들 정보와 실제 구현에 필요한 정보를 구분한다. 초안에 남은 선택은 미정으로 표시하고 사용자 요구로 확정하지 않는다.

## 1. 요청의 명확성

다음 행동이 방향 탐색, 설계 초안, 구현, 설명 중 무엇인지 확인한다. 서로 다른 해석이 서로 다른 결과를 만들 수 있는지 살핀다.

| 요청 상황 | 필요한 정보 |
|---|---|
| 방향·새 설계 | 생각의 계기와 해결할 문제, 누가 어떤 상황에서 무엇을 경험하길 원하는지, 방향이 갈릴 때의 우선순위와 제약 |
| 구현·피드백 | 바꿀 대상과 현재 상태, 원하는 변화, 충족 여부를 관찰할 완료 기준 |
| 설명·분석 | 설명할 대상과 질문, 답변이 도와야 할 이해나 판단 |

이 표는 사용자가 작성할 양식이 아니다. 짧은 요청과 기존 맥락에 정보가 있으면 충분하다. "편하게 해줘"처럼 원하는 결과를 특정할 수 없는 표현은 구체화한다. 기존 기준으로 결정할 세부사항이 빠졌다는 이유로 진행을 막지 않는다.

구현을 위임할 때는 작업 목적, 기대 결과와 기능의 연결, 완료 기준, 선택에 필요한 우선순위를 명세로 전달할 만큼 이해했는지 확인한다. 양식에 빈 항목이 있다는 이유로 질문하지 않는다. 해당하지 않는 항목이나 기존 대화와 근거로 충분한 정보는 다시 묻지 않는다. 필요한 정보가 부족하면 공통 판단 원칙에 따라 조사할 사실과 사용자에게 질문할 결정을 구분한다.

예를 들어 기존 맥락과 지정 문구가 충분한 버튼 문구 변경은 목적을 다시 묻지 않고 진행한다. "검색을 편하게"라는 요청도 기존 대화와 조사로 찾을 대상과 흐름을 정할 수 있는지 먼저 확인한다. 이를 정할 수 없고 선택에 따라 사용자 경험이 달라질 때 질문한다.

핵심 의도가 비어 있으면 생각의 계기와 원하는 장면을 사용자가 설명할 수 있게 한다. 장면·비유·선택지를 제안할 수 있으나 제안을 사용자 생각으로 확정하거나 제시한 선택지 안에서만 답하도록 제한하지 않는다.

## 2. 실제 맥락과의 적합성

관련 코드·설정·현재 동작·실행 환경·설계 근거를 필요한 범위에서 확인한다. 작은 변경은 해당 기능과 기존 패턴을 조사하고, 구조 변경은 호출부·데이터·사용 흐름까지 넓힌다. 사용자 의도가 비어 있어도 그 답과 무관한 조사는 진행한다.

다음 기준으로 요청과 확인한 맥락을 대조한다.

- 요청이 전제한 현재 상태가 조사한 사실과 맞는지 확인한다. 차이가 있으면 관찰 조건과 근거를 설명한다.
- 원하는 변화의 실행 가능성, 제약과 영향, 추가 결정이 필요한 부분을 확인한다.
- 기존 설계와 충돌하면 충돌과 영향을 밝힌다. 설계 변경 자체가 요청일 수 있으므로 충돌만으로 요청을 거절하거나 목표를 기존 구조에 맞춰 바꾸지 않는다.
- 기존 패턴으로 정할 세부사항과 사용자만 선택할 방향을 구분한다.

코드에서 확인한 동작과 실제 실행으로 관찰한 동작을 구분한다. 기록되지 않은 설계 이유는 추측으로 표시한다. 새 설계에 존재하지 않는 코드 근거를 만들지 않는다. 접근할 수 없는 환경은 확인 불가로 남기고 조사 범위 밖에 영향이 없다고 단정하지 않는다.

필요한 현재 동작 확인은 할 수 있지만 요청 검증을 코드 수정이나 전체 테스트 실행으로 확대하지 않는다. 구현 결과의 검증은 별도 책임이다.

## 3. 목표와 요청한 수단의 연결

사용자가 겪는 문제, 원하는 결과, 요청한 작업을 구분한다. 사용자가 특정 방법 자체를 원한다면 그것도 의도로 존중한다. 메인이 목표를 만들어 놓고 그 목표에 맞춰 요청을 평가하지 않는다.

요청한 작업이 무엇을 바꾸고 그 변화가 원하는 결과에 어떻게 도움이 되는지 확인한다. 알려진 목표와 관계가 분명한 작은 수정은 목적을 다시 질문하지 않는다. 해결책이 목표보다 앞섰거나 큰 변경의 효과가 불분명할 때 연결을 더 살핀다.

연결이 불분명하거나 반대 효과가 예상되면 확인한 근거와 예상되는 차이를 제시한다. 예를 들어 메모를 찾기 어려워 폴더를 더 깊게 나누려는 요청은 어려움이 분류 때문인지 검색 때문인지에 따라 효과가 달라진다. 이때 실제 사용 장면과 원하는 찾기 방식을 확인한다.

문제 범위가 크면 목표를 유지하면서 먼저 풀 작은 부분을 제안할 수 있다. 대안은 원래 요청과 함께 이유·제약을 비교하고 근거 없이 우월하다고 단정하지 않는다. 사용자가 선택한 방법의 이유가 확보되면 같은 문제를 반복해서 재심사하지 않는다. 구현 취향을 이유로 요청을 막지 않는다.

## 판단 결과

다음 행동에 필요한 만큼 이해한 결과와 완료 기준, 확인한 사실과 근거, 제약, 가정·미확인 사항, 필요한 사용자 결정을 반환한다. 결과를 보기 좋게 정리했다는 이유로 불확실성을 지우지 않는다.

정보와 근거가 충분하면 기존 작업 흐름으로 이어가며 별도 승인을 추가하지 않는다. 조사할 사실이 남으면 확인 방법을 정하고, 확인할 수 없으면 한계를 밝힌다. 결과 방향을 바꾸는 사용자 결정이 남으면 그 결정에 의존하는 실행만 보류한다. 목표를 임의로 바꾸거나 미확인을 확인된 사실로 보고하지 않는다.
