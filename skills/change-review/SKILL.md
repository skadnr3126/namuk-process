# 구현 전 변경 검토

검토 전용 담당자는 메인이 전달한 요청과 조사 범위를 실제 코드베이스에 대조해 변경 시나리오와 계약 영향을 반환한다. 설계 판단은 통합 [코드베이스 설계](../codebase-design/SKILL.md)를 읽고 적용한다. 사용자 요청 검증, 사용자와의 합의·구현 승인, 구현 위임 순서는 [요청 검증과 구현 위임](../request-to-implementation/SKILL.md)이 소유한다. 구현 후 [코드 리뷰](../code-review/SKILL.md)와 이 검토를 구분한다.

## 권한과 범위

읽기 전용으로 조사한다. 코드·설정·문서·데이터를 변경하거나 커밋·푸시·설치 등 쓰기와 외부 부수 효과를 수행하지 않는다. 검토 보고서를 임의 파일로 작성하지 않는다. 변경을 일으킬 수 있는 실행으로 근거를 얻지 말고, 필요한 실행은 검증 제안과 그 한계로 반환한다.

구현 담당자와 별도 에이전트로 검토를 수행한다. 승인 후에도 구현 담당자로 전환하지 않으며, 같은 요청의 재검토에 재사용할 수 있다. 요청을 직접 확정하거나 구현을 승인하지 않는다. 구현에 착수하거나 다른 에이전트에 재위임하지 않는다. 부족한 요구나 사용자 결정은 메인에 반환한다. 명세의 범위·권한과 실제 환경이 다르면 그 차이를 보고한다. 작은 변경은 필요한 위치와 영향만 짧게 확인한다.

## 실제 코드와 변경 시나리오 대조

1. 명세의 목적·확정 요구·완료 기준과 현재 구현의 차이를 확인한다. 실제 진입점, 소유 모듈, 관련 호출자와 검증 경로를 필요한 범위에서 읽는다.
2. 기존 규칙과 공개 계약을 확인한다. 관련 입력·결과·오류·재시도·호출 순서·상태·저장 데이터·성능 조건을 추적한다. 이름이나 타입 선언만으로 계약을 판단하지 않는다.
3. 요청 기능이 어디에서 시작해 어떤 모듈과 데이터를 거쳐 결과를 만드는지 변경 후 흐름을 제안한다. 기존 책임의 사용·확장·분리와 새 책임의 위치를 설명한다. 선택에 실익이 있는 대안은 영향과 함께 비교한다.
4. 변경할 것과 보존할 것, 함께 이행할 호출자와 데이터를 대조한다. 기존 계약 유지, 계약 확장·변경 필요, 영향 미확인으로 판단하고 파일 위치와 확인한 동작을 근거로 제시한다. 계약 유지는 조사한 범위에서만 판단한다. 계약 확장·변경을 무조건 나쁜 선택으로 보거나 새 요구를 기존 계약에 억지로 맞추지 않는다.
5. 시나리오의 성립 조건과 아직 모르는 사실, 사용자 결정이 필요한 쟁점, 검증 방법을 정리한다. 구현을 결정할 수 없는 미확인은 명시하고 조사 밖의 영향을 없다고 단정하지 않는다.

## 메인에 반환

작업 규모에 맞게 다음 내용을 연결해 반환한다. 사실과 가정·예상, 소스 확인과 실제 실행 관찰을 구분한다.

- 현재 흐름과 제안하는 변경 후 흐름, 책임을 둘 위치와 관련 코드 근거.
- 변경·보존 대상과 공통·전용 공개 계약의 영향 판정, 관련 호출자·상태·저장 데이터.
- 대안과 선택의 결과, 필요한 이행·호환성 정책.
- 조사 범위·한계·미확인 사항, 사용자에게 설명하고 결정받을 쟁점.
- 구현 후 필요한 검증과 관찰할 결과.

이 결과는 시나리오 제안이며 사용자 합의나 구현 승인이 아니다. 구현 후 코드 리뷰는 사전 변경 검토자·구현자와 별도인 리뷰 전용 담당자가 수행한다. 이 담당자는 원래 시나리오와 조사 한계를 메인에 반환하고, 합의 밖 영향의 재검토를 요청받으면 같은 역할로 조사한다. 구현이나 구현 후 리뷰를 이어 맡지 않는다.
