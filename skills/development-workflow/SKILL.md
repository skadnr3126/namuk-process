# 개발 작업 흐름

사용자 의도를 실행 가능한 요청으로 정리하고, 같은 설계 기준으로 구현한 뒤 처음의 완료 기준과 결과를 대조한다. 단계별 판단을 이어가되 작업 규모에 맞게 짧게 수행한다. 이미 확보한 의도·맥락·검증 결과를 재사용하고 단계마다 별도 승인을 요구하지 않는다.

일반 프로젝트의 개발 작업을 관리한다. 설계·검토만 요청받았다면 그 산출물까지 수행한다. 구현 요청이면 해당 범위의 설계·코드 작성·검증을 진행한다. 플러그인 자체 개선은 [담당 스킬과 공통 변경 절차](../../skill-refer.md#플러그인-개선-작업-연결)를 따른다.

## 1. 의도와 원하는 결과, 완료 기준 정리

대화에서 해결할 문제, 작업 대상과 현재 상태, 원하는 변화, 제약을 파악한다. 사용자 발언, 조사로 확인한 사실, 인공지능의 해석을 구분하고 이미 설명한 내용을 다시 묻지 않는다.

원하는 결과를 관찰할 수 있는 완료 기준으로 정리한다. 어떤 입력이나 사용 상황에서 무엇이 달라져야 하는지, 무엇으로 확인할지 짧게 명시한다. 설계만 하는 작업은 설계 산출물이 답해야 할 요구를 기준으로 삼는다. 인공지능가 제안한 해석이나 미정인 선택을 사용자 의도로 확정하지 않는다.

관련 코드·설정·현재 동작처럼 조사할 수 있는 사실은 직접 확인한다. 결과 방향을 바꾸는 사용자 의도가 빠졌을 때만 질문하고, 그 답과 무관한 조사는 계속한다. 작은 수정은 기존 맥락과 짧은 완료 기준으로 충분하며 사용자가 요청 양식을 작성할 필요는 없다.

## 2. 불확실한 부분에 필요한 요청 검증 선택

이번 요청에서 판단이 필요한 부분만 선택한다. 이미 충족한 검증을 반복하지 않는다.

- 대상·원하는 변화·완료 기준이 불분명하면 [명확성 검증](../verify-request-clarity/SKILL.md)을 사용한다.
- 코드·환경·설계에 대한 전제나 실행 가능성·영향이 불확실하면 [맥락 적합성 검증](../verify-request-context/SKILL.md)을 사용한다.
- 요청한 방법이 문제와 원하는 결과에 도움이 되는지 불분명하면 [문제와 수단의 일치 검증](../verify-request-alignment/SKILL.md)을 사용한다.

검증에서 확인한 사실과 제약을 요청과 완료 기준에 연결한다. 충분하면 설계·구현으로 진행한다. 사용자 결정이 남으면 그 결정에 의존하는 작업만 보류한다. 조사 결과를 이유로 사용자 목표를 임의로 바꾸지 않는다.

## 3. 코드베이스 설계에 따라 설계하고 구현

코드를 설계하거나 작성할 때 [코드베이스 설계](../codebase-design/SKILL.md)를 읽고 적용한다. 기존 설계 결정, 관련 모듈과 호출부, 데이터와 상태 소유권, 의존성을 확인한다. 첫 설계와 이후 코드 작성에 같은 기준을 적용한다.

변경에 필요한 모듈의 책임과 인터페이스, 의존성 처리, 영향을 받는 호출부, 유지할 동작을 짧게 정한다. 작은 수정은 기존 설계 안에서 변경 위치를 확인하는 것으로 충분하다. 실제로 필요한 구분에만 구조를 추가한다.

구현은 이 설계와 완료 기준에 맞춰 수행한다. 인터페이스를 바꾸면 관련 호출부도 함께 수정한다. 구현 중 설계 변경이 필요해지면 이유와 영향을 확인하고, 사용자 결과를 바꾸는 선택이 아니라면 범위 안에서 진행한다. 설계와 코드가 달라진 상태를 그대로 두지 않는다.

이후 작업에 필요한 설계 결정은 기존 문서에 반영한다. 새 문서는 후속 작업에서 필요한 결정을 전달할 때만 만든다. 무관한 사용자 변경을 보존하고 프로젝트의 기존 용어와 규칙을 따른다.

## 4. 실제 결과를 처음의 완료 기준과 대조

결과를 보기 전에 정한 완료 기준을 사용한다. 구현에 맞춰 기준을 낮추지 않는다. 사용자가 범위를 변경했다면 바뀐 기준과 이유를 구분한다.

변경한 동작을 모듈의 인터페이스 또는 실제 사용자 흐름으로 확인한다. 관련 기존 테스트와 프로젝트의 필수 검사를 변경 규모에 맞게 실행하고, 최종 변경 내역이 설계의 책임·인터페이스·의존성 구분을 따르는지도 확인한다. 빌드 성공만으로 사용자 동작을 입증하지 않는다. 설계만 요청된 경우에는 설계 산출물을 기준과 대조하고 구현 동작은 미확인으로 남긴다.

완료 기준별로 충족·미충족·미확인과 실제 근거를 보고한다. 소스·단위 테스트의 근거와 실제 앱·외부 시스템에서 관찰한 근거를 구분한다. 관련 범위의 실패는 원인을 수정하고 다시 확인한다. 실행할 수 없는 검증과 남은 사용자 결정은 한계로 밝히며 미확인을 완료로 보고하지 않는다.
