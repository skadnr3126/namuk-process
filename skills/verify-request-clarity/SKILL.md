# 요청의 명확성 검증

사용자가 원하는 결과를 이해할 만큼 정보가 있는지 판단한다. 요청 문장의 길이나 형식을 평가하지 않는다. 구현과 코드베이스의 적합성은 이 검증의 책임이 아니다.

## 최소 정보 확인

먼저 다음 행동이 방향 탐색, 설계 초안, 구현 중 무엇인지 구분한다. 대화와 이미 확보한 맥락을 활용하고 설명된 내용을 다시 묻지 않는다.

| 요청 상황 | 확보할 최소 정보 |
|---|---|
| 방향·새로운 설계 | 왜 이 생각을 했는지와 해결할 문제·계기, 누가 어떤 상황에서 무엇을 경험하는지 보여주는 이상적인 그림. 방향이 갈릴 때는 우선순위와 중요한 제약 |
| 구현·피드백 | 바꿀 대상과 현재 상태, 원하는 변화, 요청을 충족했는지 판단할 완료 기준 |

이 항목들은 사용자가 작성할 양식이 아니다. 짧은 요청에 이미 포함돼 있거나 기존 맥락으로 확인되면 충분하다. 현재 동작처럼 조사로 알아낼 정보는 사용자에게 설명을 요구하지 말고 조사할 항목으로 구분한다.

답이 있다는 사실보다, 다른 해석이 서로 다른 결과를 만들 수 있는지 살핀다. "편하게 해줘"처럼 결과를 특정할 수 없는 표현은 구체화가 필요하다. 반대로 기존 기준으로 결정할 세부사항은 빠졌다는 이유만으로 실행을 막지 않는다.

## 생각을 받는 방법

사용자만 정할 수 있는 의도가 비어 있으면, 왜 이 생각을 했는지와 원하는 그림을 먼저 펼칠 공간을 준다. 질문은 다음 행동을 결정하는 빈칸에 집중한다. 표현을 돕는 장면·비유·선택지를 제안할 수 있지만, 인공지능의 제안을 사용자 생각으로 확정하거나 제시한 선택지 안에서만 답하도록 제한하지 않는다.

맥락이 적은 새로운 설계에는 높은 기준을 적용한다. 성숙한 코드베이스의 작은 변경에는 관련된 기존 맥락을 활용한다. 설계 초안을 만들 만큼 충분한 정보와 실제 구현에 충분한 정보는 구분한다.

## 판단과 다음 행동

이해한 결과와 다음 행동을 짧게 전달한다. 정보가 충분하면 기존 작업 흐름으로 이어가며 별도 승인을 추가하지 않는다. 조사할 사실이 남으면 무엇을 확인할지 정하고, 핵심 의도가 빠졌으면 왜 그 답이 결과를 바꾸는지 설명하며 질문한다.

답을 기다리는 동안 그 결정에 의존하는 실행만 보류한다. 무관한 조사와 생각 정리는 계속할 수 있다. 미정인 선택은 초안에서도 미정으로 표시한다. 정돈된 요청 문서가 나왔다는 이유만으로 사용자의 생각을 이해했다고 판단하지 않는다.
