# Namuk Process skill creator

Namuk Process의 플러그인 철학에 맞는 작고 구체적인 스킬을 추가하거나 기존 스킬을 수정한다. 스킬은 특정 상황에서 반복 사용할 판단과 작업 방법을 담는다.

## 먼저 구조를 파악한다

1. `.codex-plugin/plugin.json`, `플러그인철학.md`, 스킬 목록, 변경 대상 스킬과 연결된 참조를 읽는다.
2. 사용자가 해결하려는 반복 문제, 원하는 결과, 적용 범위, 권한 제한을 현재 대화에서 추출한다. 이미 답이 있는 내용은 다시 묻지 않는다. 방향을 결정할 정보가 빠졌을 때만 질문한다.
3. 새 스킬이 꼭 필요한지 판단한다. 기존 스킬에 몇 줄을 추가하거나 기존 스킬을 참조해 연결할 수 있으면 재사용한다. 기능이 겹치는 스킬을 복제하지 않는다.

## 책임과 연결을 설계한다

새 스킬은 한 가지 알아볼 수 있는 목적과 소유 책임을 갖는다. 다음 경계를 분명하게 작성한다.

- 언제 적용하며 어떤 비슷한 요청에서는 적용하지 않는가.
- 어떤 입력과 권한을 전제로 하는가.
- 스킬이 직접 판단·수정하는 범위는 어디까지인가.
- 기존 스킬이나 담당자에게 무엇을 넘기고 어떤 결과를 돌려받는가.
- 작업 실패, 검증 불가, 외부 작업 제한 시 어디서 멈추는가.

이미 담당자가 있는 단계는 다시 구현하지 말고 해당 스킬로 연결한다. 예를 들어 플러그인 사용에서 개선점을 찾아 고치는 흐름은 `reflect`, 플러그인 변경을 기존본과 비교하는 검증은 `verify-improvement`, 준비된 변경을 커밋하고 PR로 보내는 흐름은 `submit-improvement`가 맡는다. 경계를 바꿀 때 관련 스킬도 함께 읽고 호출 관계가 순환하지 않는지 확인한다.

## 서브에이전트 사용

서브에이전트를 활용하되 역할을 나눈다. 메인 또는 담당 에이전트는 사용자 맥락과 변경을 책임지고, 독립 평가가 유용한 경우에만 새로운 맥락 없는 검증 에이전트를 둔다. 검증 에이전트에는 결론을 유도하는 해결안이나 성공 주장을 전달하지 않는다. 같은 작업을 여러 에이전트가 동시에 수정하지 않게 소유 파일과 worktree를 정한다. 분리의 이득이 작은 문구 수정에는 에이전트를 추가하지 않는다.

## 최소한으로 작성한다

- 이름은 소문자 kebab-case로 짧고 목적을 알아볼 수 있게 한다. 폴더명과 frontmatter `name`을 일치시킨다.
- `description`은 고유한 사용 시점과 제외 경계를 간결하게 알려 자동 선택이 엉뚱한 요청에 퍼지지 않게 한다.
- 본문에는 실제 판단에 필요한 목적, 입력, 작업 순서, 소유권, 안전 경계, 결과 전달만 둔다. 이미 시스템 지침에 있는 일반론이나 같은 말을 반복하지 않는다.
- 기본 작업 절차는 `SKILL.md` 하나에 둔다. 실제로 선택적으로 읽을 상세 자료가 있을 때만 `references/`를 추가하고 링크와 사용 시점을 적는다. 빈 디렉터리나 미래를 위한 틀은 만들지 않는다.
- 확인되지 않은 사용자 선호를 사실처럼 굳히지 않는다. 외부 서비스, 계정, 비용, 게시, 커밋·push 같은 효과는 사용자가 정한 권한 경계를 유지한다.
- 기존 스킬 수정은 요청된 목적에 필요한 파일만 바꾸고 다른 규칙·메타데이터를 보존한다.

## 검증한다

변경 후 manifest와 스킬의 YAML frontmatter, 이름·폴더 일치, 설명 길이, 내부 참조 경로를 확인하고 사용 가능한 skill validator를 실행한다. diff와 공백 오류도 검토한다.

검증은 변경 영향에 맞춘다. 링크·문구만 바뀌면 문맥과 링크 확인으로 마친다. 자동 선택, 호출 흐름, 도구 행동을 바꾸면 발동 사례와 비발동 사례를 각각 하나 이상 사용해 실제 결과를 확인한다. 플러그인의 개선 효과 자체가 변경 목표이면 [verify-improvement](../verify-improvement/SKILL.md)를 사용해 기존본과 변경본을 비교한다. 형식 검사를 행동 검증이라고 부르지 않는다.

완료 시 추가·수정한 스킬, 재사용한 기존 스킬, 수행한 검증과 남은 한계를 짧게 보고한다.
