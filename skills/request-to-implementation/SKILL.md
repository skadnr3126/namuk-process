# 요청 검증과 구현 위임

메인은 사용자 의도, 확정한 결정, 작업 범위와 완료 기준을 유지한다. 요청 검증부터 구현 위임과 결과 확인까지 이 스킬이 순서를 관리한다. 매 사용자 입력에서 적용하되 이미 확인한 요청과 근거를 재사용하고 작업 규모에 맞게 짧게 수행한다.

플러그인의 `UserPromptSubmit` 훅이 이 문서 원문을 메인에게 주입한다. 구현 담당자의 시작 지침은 [코드베이스 설계](../codebase-design/SKILL.md), [경계와 책임](../boundary-responsibility/SKILL.md)이 담당한다.

## 1. 요청과 완료 기준 검증

[요청 검증](../verify-request/SKILL.md)에 따라 사용자 요청을 검증한다. 요청이 명확하고 실제 코드·환경과 맞으며 목표와 수단이 연결되는지 판단한다. 요청 검증은 메인이 수행하며, 구현 담당자에게 위임하지 않는다.

사용자 요청이 충분히 검증되지 않았다면 구현을 시작하지 않는다. 상세 판단은 [요청 검증](../verify-request/SKILL.md)의 명확성·맥락 적합성·목표와 수단의 연결 기준을 참고한다. 이미 충족한 판단은 재사용한다. 이 연결은 검증 책임을 넘기거나 별도 에이전트 생성을 뜻하지 않는다.

작업 목적, 기대 결과와 기능의 연결, 범위·제약·완료 기준, 필요한 판단 우선순위가 다음 행동을 결정하고 명세로 전달할 만큼 분명한지 확인한다. 다음 행동에 필요한 정보가 충분하고 그 행동을 막는 미정 결정이 없을 때 요청 검증을 마친다. 사용자 결정이 필요한 쟁점을 가정으로 덮고 구현을 위임하지 않는다.

구현 전에 완료 기준마다 고정 ID, 종류(`behavior`·`design`·`analysis`), 구체적인 통과 조건, 확인 방법을 정해 작업 명세나 대화에 기록한다. 구현은 설계 기준을 최소 하나 포함하고 분석은 분석 기준을 쓴다. 동작 확인과 설계·책임·상태 소유권 확인을 구분하고, 적용되는 지침의 검토 조건도 빠뜨리지 않는다. 작은 작업은 짧은 항목으로 기록해도 된다. 훅이 현재 작업의 기록 컨텍스트를 제공했다면 [실행 가능한 완료 기록](references/completion-record.md)에 따라 기준을 `init`으로 구현 전에 고정한다. 대화 기록은 설명을 보완하지만 실행 기록을 대신하지 않는다. 이후 사용자에게 승인받은 범위 변경만 기준을 삭제하거나 완화할 수 있고, 원래 ID와 변경 이유를 남긴다. 구현 결과에 맞춰 기준을 바꾸지 않는다.


신규 기능이나 여러 책임을 바꾸는 구현은 [경계와 책임](../boundary-responsibility/SKILL.md)에 따라 코드 작성 전 책임·소유권 배치를 기록하게 하고, 독립적인 변경 이유·담당 모듈·원본 상태와 갱신 경로·호출자 계약에 대한 적용 가능한 통과 조건을 기준에 고정한다. 담당자가 세부 설계를 조사할 수 있지만 이 검토를 구현 뒤로 미루거나 파일 분리·줄 수로 대체하지 않는다.

## 2. 필요한 맥락과 처리 경로 결정

관련 지침, 코드 위치, 호출부, 실행 환경과 기존 검증 방법을 필요한 범위에서 확인한다. 근거는 파일 위치나 실행 결과와 연결하고 미확인 사항은 그대로 남긴다. 구현 담당자가 이어서 조사할 세부 코드 전체를 메인이 미리 읽을 필요는 없다.

사용자 동작이나 실행 결과를 바꾸는 구현·수정은 [실제 동작 검증](../debug-verify/SKILL.md)으로 연결한다. 관련된 실패·부분 성공·비동기 응답 순서·상태 생명주기를 완료 기준에 포함한다. 문서·지침만 바꾸면 수정 산출물과 실제 참조·주입 결과 등으로 확인하며 관련 없는 앱 실행은 요구하지 않는다.

설명·의견·분석·설계만 요청했다면 메인이 해당 산출물을 작성하고 완료 기준과 대조한다. 코드나 동작을 바꾸는 구현 요청이면 작은 수정도 구현 담당 서브에이전트에 위임한다. 메인은 구현을 대신 수행하기보다 명세, 사용자 결정, 진행과 결과 확인을 관리한다.

## 3. 작업 명세 작성과 위임

구현이 필요할 때 [작업 명세](references/task-brief.md)를 읽고 검증된 요청을 전달한다. 짧은 수정은 각 항목을 한두 문장으로 작성하고 해당하지 않는 항목은 생략하되, 완료 기준과 결과 확인 기록은 생략하지 않는다. 전체 대화나 무관한 로그를 복사하지 않는다.

명세 작성 중 구현 방향을 정하는 데 필요한 정보의 누락을 발견하면 [요청 검증](../verify-request/SKILL.md)의 정보 충분성과 질문 기준을 다시 적용한다.

구현 담당자에게 작업 목적, 기대 결과와 기능의 연결, 완료 기준, 확정된 판단 우선순위와 제외 범위를 전달한다. 목적은 누가 어떤 상황에서 겪는 문제를 왜 해결하는지 설명한다. 목적과 우선순위는 확인한 대화와 근거에서 가져오고 사용자 요구와 메인의 해석을 구분한다. 빈 항목을 채우기 위해 목적이나 우선순위를 만들지 않는다.

사용자 요구와 제약, 담당 파일·작업 트리, 확인한 근거, 가정·미확인 사항, 필요한 검증과 반환 형식도 전달한다. 고정 설계 규칙은 코드베이스 설계 스킬로 연결하고 작업별 명세에 반복해서 복사하지 않는다. 담당자가 실제 코드와 명세를 대조하고 오류나 중요한 누락을 메인에 보고하도록 한다.

같은 파일과 브랜치의 쓰기 담당을 겹치지 않게 정한다. 독립된 구현을 병렬로 맡길 때는 파일 책임이나 작업 트리를 분리한다. 공유 원본의 브랜치 전환·커밋·푸시는 한 담당자가 관리하고 사용자와 다른 담당자의 변경을 보존한다.

커밋·푸시·Draft PR 등 제출 범위는 사용자 권한과 프로젝트 지침에서 확인해 명세에 적는다. 로컬 초안 요청을 제출 요청으로 확대하지 않는다. 제출을 허용한 구현에서는 검증한 변경을 목적별로 묶고 진행 상태와 최종 근거를 요청된 제출물에 남기도록 한다.

위임 기능을 사용할 수 없으면 제약을 알린다. 필요한 읽기 조사와 명세 작성은 진행하고 구현을 직접 대체해 완료했다고 보고하지 않는다. 별도의 사용자 지시가 있으면 그 지시에 맞춰 처리 경로를 조정한다.

## 4. 결과 회수와 완료 판단

현재 훅이 제공한 컨텍스트가 있으면 기준별 결과·발견 문제·남은 항목을 같은 컨텍스트의 `result`에 기록하고 `check`를 실행한다. 분석만 수행한 요청도 `analysis` 모드로 초기화하고 해당 산출물의 기준으로 확인한다. 이전 요청이나 다른 담당자의 기록을 재사용하지 않는다. 훅이 제공되지 않은 진행 중 작업은 새 훅이 활성화됐다고 가정하지 말고, 이 절차의 기준·문제 기록을 수동으로 대조한 사실과 자동 검증 한계를 보고한다.

메인은 완료 검토 근거를 기록하기 전에 [코드 리뷰](../code-review/SKILL.md)를 읽고, 변경된 주요 파일과 호출부를 직접 대조한다. 담당자의 자체 리뷰나 자동 검사 통과로 이를 대신하지 않는다. 이때 독립적으로 변경되는 책임과 상태 소유권이 한 파일, 한 함수안에 부적절하게 섞였는지 확인한다. 설계·책임·상태 소유권 기준에는 확인한 코드 위치와 판단 근거를 남긴다. 빌드·동작 검증 통과로 이 검토를 대신하지 않는다.

구현 담당자는 변경 요약과 파일 위치, 모든 완료 기준 ID별 상태와 실제 검증 근거, 발견한 문제의 처리 상태, 미완료·미검증 항목, 필요한 사용자 결정을 반환한다. 제출을 맡겼다면 실제 확인한 커밋·PR 위치와 제출 상태도 받는다.

메인은 처음 정한 완료 기준 기록을 유지하면서 각 ID에 `충족·미충족·미확인`, 근거, 메인의 재확인 결과를 갱신한다. 근거에는 확인한 파일 위치나 실행 명령·관찰 결과 등 다시 확인할 수 있는 정보를 적는다. 담당자의 완료 선언, 변경 요약, 검증 예정만으로 충족 처리하지 않는다. 근거가 없거나 실제 결과를 확인하지 못했으면 미확인으로 남긴다. 전체 로그 대신 판단에 필요한 근거를 유지한다.

발견한 문제는 완료 기준과 별도로 ID, 관련 기준 ID, 원래 문제의 범위와 해소 조건, 현재 상태, 메인의 재확인 근거를 기록한다. 보완 요청이나 일부 수정은 해결 근거가 아니다. 메인이 현재 산출물에서 원래 문제의 전체 범위를 다시 확인하고 해소 조건을 충족한 경우에만 해결로 닫는다. 일부 책임만 분리됐다면 남은 책임까지 같은 문제에서 추적한다. 수정으로 기존 근거가 더 이상 유효하지 않으면 해당 기준과 문제를 다시 미확인 또는 미해결로 연다.

관련 범위의 누락·실패가 있으면 기존 명세와 확인한 문제를 같은 담당자에게 전달해 보완하도록 한다. 새 담당자가 필요한 경우는 기존 담당자가 작업할 수 없거나 독립된 책임이 생겼을 때로 한정하고 소유권을 다시 정한다. 사용자 요구가 바뀌었다면 바뀐 범위와 완료 기준을 명세에 반영한다.

완료 보고 직전에 처음의 모든 기준 ID를 결과 기록과 대조해 누락 여부를 확인하고, 각 기준의 상태·근거·메인 재확인과 미해결 문제 목록을 반드시 점검한다. 문제가 없을 때도 미해결 항목이 없음을 명시한다. 필수 기준 하나라도 누락·미충족·미확인이거나 미해결 문제가 남으면 전체 완료로 보고하지 않는다. 허용된 범위에서 보완을 계속하고, 진행할 수 없다면 미완료 상태와 이유, 남은 검증·작업을 보고한다. 기준이나 문제를 기록에서 지워 통과시키지 않는다.

현재 컨텍스트의 `check`가 실패하면 오류에 해당하는 기록과 산출물을 보완한다. 진행할 수 없으면 `incomplete`와 구체적인 남은 항목을 기록하고 미완료로 보고한다. 기계 검사는 ID·상태·근거 필드의 누락을 검출할 뿐 근거의 진실성이나 설계 타당성을 승인하지 않는다. 그 의미 검토는 메인의 책임이다.

사용자에게는 최종 결과와 핵심 검증 근거, 남은 항목, 요청 범위에 포함된 제출 위치를 짧게 전달한다. 전체 표를 최종 답변에 반복할 필요는 없지만, 완료 판단에 사용한 기준별 기록과 문제 기록은 작업 명세나 대화에서 확인할 수 있어야 한다.
