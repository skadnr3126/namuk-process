# 요청 검증과 구현 위임

메인은 사용자 의도, 확정한 결정, 작업 범위와 완료 기준을 유지한다. 요청 검증부터 구현 전 변경 검토, 사용자 합의와 구현 위임, 결과 확인까지 이 스킬이 순서를 관리한다. 매 사용자 입력에서 적용하되 이미 확인한 요청과 근거를 재사용하고 작업 규모에 맞게 짧게 수행한다.

플러그인의 `UserPromptSubmit` 훅이 이 문서 원문을 메인에게 주입한다. 메인과 담당자의 설계 판단은 통합 [코드베이스 설계](../codebase-design/SKILL.md)가 담당한다. 훅이 같은 원본을 전달하며 수신자는 맡은 역할과 작업 규모에 맞게 적용한다.

## 1. 요청과 완료 기준 검증

[요청 검증](../verify-request/SKILL.md)에 따라 사용자 요청을 검증한다. 요청이 명확하고 실제 코드·환경과 맞으며 목표와 수단이 연결되는지 판단한다. 요청 검증은 메인이 수행하며, 구현 담당자에게 위임하지 않는다.

사용자 요청이 충분히 검증되지 않았다면 구현을 시작하지 않는다. 상세 판단은 [요청 검증](../verify-request/SKILL.md)의 명확성·맥락 적합성·목표와 수단의 연결 기준을 참고한다. 이미 충족한 판단은 재사용한다. 이 연결은 검증 책임을 넘기거나 별도 에이전트 생성을 뜻하지 않는다.

작업 목적, 기대 결과와 기능의 연결, 범위·제약·완료 기준, 필요한 판단 우선순위가 다음 행동을 결정하고 명세로 전달할 만큼 분명한지 확인한다. 다음 행동에 필요한 정보가 충분하고 그 행동을 막는 미정 결정이 없을 때 요청 검증을 마친다. 사용자 결정이 필요한 쟁점을 가정으로 덮고 구현을 위임하지 않는다.


## 2. 필요한 맥락과 처리 경로 결정

관련 지침, 코드 위치, 호출부, 실행 환경과 기존 검증 방법을 필요한 범위에서 확인한다. 근거는 파일 위치나 실행 결과와 연결하고 미확인 사항은 그대로 남긴다. 구현 담당자가 이어서 조사할 세부 코드 전체를 메인이 미리 읽을 필요는 없다.

설명·의견·분석·설계만 요청했다면 메인이 해당 산출물을 작성하고 완료 기준과 대조한다. 코드나 동작을 바꾸는 구현 요청이면 작은 수정도 먼저 검토 전용 서브에이전트에게 변경 검토를 맡기고, 사용자 합의와 구현 승인을 확인한 뒤 구현 전용 서브에이전트에 위임한다. 메인은 구현을 대신 수행하기보다 명세, 사용자 결정, 진행과 결과 확인을 관리한다.

## 3. 구현 전 변경 검토와 사용자 합의

명확한 코드·동작 변경 요청은 [변경 검토](../change-review/SKILL.md)를 명시적으로 읽도록 검토 전용 서브에이전트에 위임한다. 요청 자체의 검증은 메인 책임으로 유지한다. 검토자는 구현 담당자와 별도 에이전트로 두고, 읽기 전용으로 변경 시나리오와 계약 영향을 제안하며 구현하거나 승인하지 않는다. 승인 후에도 검토자에게 구현을 이어 맡기지 않고 구현 담당자에게 명세를 전달한다.

검토 명세에는 목적, 확정된 요구와 완료 기준, 조사 범위와 저장소, 확인한 근거, 제약·가정·미확인 사항, 읽기 전용 권한과 필요한 반환 결과를 담는다. 고정 설계 기준은 통합 코드베이스 설계로 연결한다. 작은 변경은 짧게 전달하고 별도 보고서 파일을 요구하지 않는다.

메인은 반환된 시나리오와 근거를 실제 관련 코드에 대조한다. 사용자에게 현재 흐름과 변경 후 흐름, 책임을 둘 위치, 변경·보존 대상, 영향받는 호출자·데이터, 검증 계획과 남은 결정을 설명한다. 사전 검토자의 제안이나 구현 후 리뷰 결과를 사용자 승인으로 취급하지 않는다.

| 계약 영향 판단 | 구현 전 진행 |
|---|---|
| 확인한 범위에서 기존 계약 유지 | 유지 판단의 근거와 조사 한계, 변경 시나리오와 검증 계획을 설명하고 구현 승인을 받는다. |
| 계약 확장·변경 필요 | 현재 계약, 변경 이유, 대안, 호출자·데이터 영향과 이행·보존 정책을 사용자와 검토하고 변경 범위 합의 및 구현 승인을 받는다. |
| 영향 미확인 | 필요한 조사를 이어가거나 확인 한계를 밝힌다. 안전한 방향을 결정할 수 없는 미확인이 남으면 그 영향에 의존하는 구현을 보류한다. |

공통 계약은 타입과 함수 외에도 규칙·오류 의미·재시도·호출 순서·상태·성능 조건을 포함한다. 계약 변경을 무조건 피하지 말고 기존 계약 유지안과 변경안을 필요한 만큼 비교한다. 공개 동작, 책임 배치, 작업 범위와 보존·이행 정책은 사용자와 판단한다. 승인한 범위 안의 내부 함수명이나 보조 코드 구성은 담당자가 판단한다.

최초의 구현 요청만으로 아직 제시하지 않은 시나리오까지 승인됐다고 가정하지 않는다. 사용자가 이미 검토한 구체 시나리오와 범위를 승인했다면 그 근거를 재사용한다. 범위와 영향에 실질적인 변화가 없으면 같은 검토나 승인을 반복하지 않는다. 답변이 없거나 시간이 지났다는 이유로 승인됐다고 판단하지 않는다.

구현 중 합의 밖의 계약 변경이나 중요한 영향을 발견하면 해당 변경의 구현을 보류하고 메인에 근거를 보고한다. 메인은 같은 검토 담당자에게 재검토를 요청하고 사용자와 필요한 범위를 다시 합의한다. 그 결정에 의존하지 않는 조사와 이미 승인된 독립 작업은 계속할 수 있다.

사전 변경 검토·구현·구현 후 리뷰 담당자는 명세 기반으로 위임하는 별도 역할이다. 전용 스킬이 OS의 읽기 전용 환경을 만들거나 훅이 승인 단계를 기술적으로 강제한다고 가정하지 않는다.

## 4. 작업 명세 작성과 구현 위임

사용자 합의와 구현 승인을 확인하면 [작업 명세](references/task-brief.md)를 읽고 검증된 요청을 전달한다. 짧은 수정은 각 항목을 한두 문장으로 작성하고 해당하지 않는 항목은 생략한다. 전체 대화나 무관한 로그를 복사하지 않는다.

명세 작성 중 구현 방향을 정하는 데 필요한 정보의 누락을 발견하면 [요청 검증](../verify-request/SKILL.md)의 정보 충분성과 질문 기준을 다시 적용한다.

구현 담당자에게 작업 목적, 기대 결과와 기능의 연결, 완료 기준, 확정된 판단 우선순위와 제외 범위를 전달한다. 목적은 누가 어떤 상황에서 겪는 문제를 왜 해결하는지 설명한다. 목적과 우선순위는 확인한 대화와 근거에서 가져오고 사용자 요구와 메인의 해석을 구분한다. 빈 항목을 채우기 위해 목적이나 우선순위를 만들지 않는다.

사용자 요구와 제약, 담당 파일·작업 트리, 확인한 근거, 가정·미확인 사항, 필요한 검증과 반환 형식도 전달한다. 승인된 변경 시나리오, 사용자 합의와 구현 승인 근거, 허용한 계약 변경, 보존할 계약·데이터, 영향받는 호출자와 재협의 조건을 명세에 담는다. 고정 설계 규칙은 코드베이스 설계 스킬로 연결하고 작업별 명세에 반복해서 복사하지 않는다. 담당자가 실제 코드와 명세를 대조하고 오류나 중요한 누락을 메인에 보고하도록 한다.

같은 파일과 브랜치의 쓰기 담당을 겹치지 않게 정한다. 독립된 구현을 병렬로 맡길 때는 파일 책임이나 작업 트리를 분리한다. 공유 원본의 브랜치 전환·커밋·푸시는 한 담당자가 관리하고 사용자와 다른 담당자의 변경을 보존한다.

커밋·푸시·Draft PR 등 제출 범위는 사용자 권한과 프로젝트 지침에서 확인해 명세에 적는다. 로컬 초안 요청을 제출 요청으로 확대하지 않는다. 제출을 허용한 구현에서는 검증한 변경을 목적별로 묶고 진행 상태와 최종 근거를 요청된 제출물에 남기도록 한다.

위임 기능을 사용할 수 없으면 제약을 알린다. 필요한 읽기 조사와 명세 작성은 진행하고 구현을 직접 대체해 완료했다고 보고하지 않는다. 별도의 사용자 지시가 있으면 그 지시에 맞춰 처리 경로를 조정한다.

## 5. 구현 결과 회수와 독립 리뷰 위임

구현 담당자는 변경 요약과 파일 위치, 완료 기준별 충족 여부와 검증 근거, 미완료·미검증 항목, 필요한 사용자 결정을 반환한다. 제출을 맡겼다면 실제 확인한 커밋·PR 위치와 제출 상태도 받는다.

메인은 반환 결과와 실제 변경 범위를 확인한 뒤 사전 변경 검토자·구현자와 별도인 구현 리뷰 전용 서브에이전트를 생성한다. [코드 리뷰](../code-review/SKILL.md)의 실제 원본 경로와 상대 참조 기준 폴더를 명시해 읽도록 하고, [구현 리뷰 명세](../code-review/references/implementation-review-brief.md)를 읽어 승인된 시나리오·완료 기준·저장소·기준 버전·실제 변경 범위·관련 호출자·검증 근거와 미확인을 전달한다. 이 전용 절차를 모든 담당자에게 주입하지 않으며 종료 훅으로 실행하지 않는다.

미추적 신규 파일과 기존 사용자 변경도 구분해 전달한다. 메인은 쓰기 담당과 시점을 조정해 리뷰 중 대상이 바뀌지 않게 한다. 리뷰 담당자는 실제 최종 diff·신규 파일·호출부를 읽기 전용으로 확인하고 메인에만 결과를 반환하며 직접 수정·커밋·푸시·승인·완료 판단·추가 위임을 하지 않는다.

위임 기능을 사용할 수 없거나 리뷰가 실패·중단되면 원인과 남은 리뷰를 미완료로 기록한다. 담당자의 완료 선언이나 빌드 성공으로 독립 리뷰를 대신하거나 실패·미수행·미확인을 통과로 바꾸지 않는다.

## 6. 리뷰 의견 보완과 최종 완료 판단

메인은 검토한 버전과 범위, 발견사항의 조건·근거·심각성, 검증 한계를 승인된 시나리오와 완료 기준에 대조한다. 채택 여부와 이유를 판단하고 필요한 보완은 기존 명세와 함께 같은 구현 담당자에게 전달한다. 리뷰 담당자에게 수정을 맡기지 않는다. 승인 범위 안의 보완은 재승인을 요구하지 않는다. 합의 밖 계약 변경이나 중요한 영향을 요구하는 의견은 해당 변경을 보류하고 같은 사전 변경 검토자와 사용자 합의 경로로 처리한다.

구현 담당자의 보완·검증 결과를 회수하면 같은 독립 리뷰 담당자에게 달라진 최종 변경과 관련 영향을 전달해 재검토를 요청한다. 이전 지적의 해결·미해결·미확인과 추가 발견사항을 구분한다. 리뷰 이후 다시 바뀐 변경에도 이 절차를 적용하고 이전 버전의 리뷰를 최종 결과의 통과 근거로 쓰지 않는다.

최종 완료는 메인이 판단한다. 실제 변경과 관련 호출자를 통합 설계 기준에 대조하고 승인된 범위, 보존할 계약·데이터, 완료 기준별 검증 근거와 독립 리뷰 결과를 확인한다. 빌드 성공이나 담당자의 완료 선언만으로 사용자 동작을 확인했다고 판단하지 않는다. 세부 로그 전체보다 판단에 필요한 근거를 유지한다.

관련 범위의 누락·실패가 있으면 기존 명세와 확인한 문제를 같은 담당자에게 전달해 보완하도록 한다. 새 담당자가 필요한 경우는 기존 담당자가 작업할 수 없거나 독립된 책임이 생겼을 때로 한정하고 소유권을 다시 정한다. 사용자 요구가 바뀌었다면 바뀐 범위와 완료 기준을 명세에 반영한다.

미확인을 충족으로 바꾸거나 구현에 맞춰 완료 기준을 낮추지 않는다. 필요한 검증을 실행할 수 없으면 완료한 부분과 검증 불가 이유, 남은 작업을 구분해 보고한다. 사용자에게 최종 결과와 검증 근거, 한계, 요청 범위에 포함된 제출 위치를 짧게 전달한다.
