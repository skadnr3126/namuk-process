# 요청 검증과 구현 위임

메인은 사용자 의도, 확정한 결정, 작업 범위와 완료 기준을 유지한다. 요청 검증부터 구현 위임과 결과 확인까지 이 스킬이 순서를 관리한다. 매 사용자 입력에서 적용하되 이미 확인한 요청과 근거를 재사용하고 작업 규모에 맞게 짧게 수행한다.

플러그인의 `UserPromptSubmit` 훅이 이 문서 원문을 메인에게 주입한다. 설치 환경에서 훅을 신뢰하고 실행해야 자동 주입이 동작한다. 구현 담당자의 시작 지침은 [코드베이스 설계](../codebase-design/SKILL.md)가 담당한다.

## 1. 요청과 완료 기준 검증

사용자가 해결하려는 문제, 작업 대상, 원하는 결과, 제약과 허용한 작업 범위를 확인한다. 각 입력에서 명확성, 실제 맥락과의 적합성, 문제와 수단의 연결을 내부적으로 점검한다. 검증을 위해 매번 질문하거나 같은 사실을 다시 조사하지 않는다.

어떤 입력이나 상황에서 무엇이 달라져야 하는지 관찰 가능한 완료 기준을 정한다. 설명·분석·설계 요청도 요청한 산출물의 기준을 정하되 코드 변경을 전제하지 않는다. 사용자 요구, 조사로 확인한 사실, 메인의 해석과 가정을 구분한다.

관련 코드·설정·현재 동작처럼 조사할 수 있는 사실은 직접 확인한다. 사용자만 정할 수 있고 다음 행동의 방향을 바꾸는 정보가 빠졌을 때만 질문한다. 답변이 필요한 작업만 보류하고 독립적인 조사는 계속한다. 메인의 가정을 사용자 요구로 확정하거나 조사 결과를 이유로 사용자 목표를 바꾸지 않는다.

상세 판단은 [요청 검증](../verify-request/SKILL.md)의 명확성·맥락 적합성·목표와 수단의 연결 기준을 참고한다. 이미 충족한 판단은 재사용한다. 이 연결은 검증 책임을 넘기거나 별도 에이전트 생성을 뜻하지 않는다.

목표·범위·제약·완료 기준이 다음 행동을 결정할 만큼 분명하고, 남은 불확실성이 진행을 막는지 판단했으면 요청 검증을 마친다. 사용자 결정이 필요한 쟁점을 가정으로 덮고 구현을 위임하지 않는다.

## 2. 필요한 맥락과 처리 경로 결정

관련 지침, 코드 위치, 호출부, 실행 환경과 기존 검증 방법을 필요한 범위에서 확인한다. 근거는 파일 위치나 실행 결과와 연결하고 미확인 사항은 그대로 남긴다. 구현 담당자가 이어서 조사할 세부 코드 전체를 메인이 미리 읽을 필요는 없다.

설명·의견·분석·설계만 요청했다면 메인이 해당 산출물을 작성하고 완료 기준과 대조한다. 코드나 동작을 바꾸는 구현 요청이면 작은 수정도 구현 담당 서브에이전트에 위임한다. 메인은 구현을 대신 수행하기보다 명세, 사용자 결정, 진행과 결과 확인을 관리한다.

프로젝트의 feature map과 관련 wiki를 찾아 기능, 코드 위치와 검증 방법을 확인한다. 기존 문서 경로를 유지한다. 문서가 없다면 공통 색인은 `docs/feature-map.md`, 기능별 문서는 `docs/features/<기능>.md`, 설계 이유와 제약을 별도로 설명할 wiki는 `docs/wiki/<주제>.md`를 기본으로 삼는다. 이번 작업과 관련된 문서만 만들고 전체 기능 목록을 추측해 채우지 않는다. 문서의 설명은 실제 코드와 대조한다.

## 3. 작업 명세 작성과 위임

구현이 필요할 때 [작업 명세](references/task-brief.md)를 읽고 검증된 요청을 전달한다. 짧은 수정은 각 항목을 한두 문장으로 작성하고 해당하지 않는 항목은 생략한다. 전체 대화나 무관한 로그를 복사하지 않는다.

구현 담당자에게 목표와 완료 기준, 사용자 요구와 제약, 담당 파일·작업 트리, 확인한 근거, 가정·미확인 사항, 필요한 검증과 반환 형식을 전달한다. 고정 설계 규칙은 코드베이스 설계 스킬로 연결하고 작업별 명세에 반복해서 복사하지 않는다. 담당자가 실제 코드와 명세를 대조하고 오류나 중요한 누락을 메인에 보고하도록 한다.

같은 파일과 브랜치의 쓰기 담당을 겹치지 않게 정한다. 독립된 구현을 병렬로 맡길 때는 파일 책임이나 작업 트리를 분리한다. 공유 원본의 브랜치 전환·커밋·푸시는 한 담당자가 관리하고 사용자와 다른 담당자의 변경을 보존한다.

명세에 시작할 때 읽을 공통 색인과 관련 기능 문서·wiki 경로, 구현 담당자가 갱신할 문서 범위를 지정한다. 기능별 문서와 wiki의 쓰기 담당은 하나씩 정한다. 공통 색인은 메인만 수정한다. 색인이 없으면 위임 전에 메인이 이번 작업의 기능과 문서 경로를 담은 최소 색인을 만든다. 담당자는 검증 후 자기 문서를 갱신하고 공통 색인의 추가·수정·삭제·이름 변경 제안을 근거와 함께 반환한다. 문서가 없으면 생성할 경로와 소유권도 명세에 정한다.

커밋·푸시·Draft PR 등 제출 범위는 사용자 권한과 프로젝트 지침에서 확인해 명세에 적는다. 로컬 초안 요청을 제출 요청으로 확대하지 않는다. 제출을 허용한 구현에서는 검증한 변경을 목적별로 묶고 진행 상태와 최종 근거를 요청된 제출물에 남기도록 한다.

위임 기능을 사용할 수 없으면 제약을 알린다. 필요한 읽기 조사와 명세 작성은 진행하고 구현을 직접 대체해 완료했다고 보고하지 않는다. 별도의 사용자 지시가 있으면 그 지시에 맞춰 처리 경로를 조정한다.

## 4. 결과 회수와 완료 판단

구현 담당자는 변경 요약과 파일 위치, 완료 기준별 충족 여부와 검증 근거, 미완료·미검증 항목, 필요한 사용자 결정을 반환한다. 제출을 맡겼다면 실제 확인한 커밋·PR 위치와 제출 상태도 받는다.

메인은 반환 결과를 처음의 완료 기준과 대조하고 필요한 변경 내역과 실제 근거를 확인한다. 담당자의 완료 선언이나 빌드 성공만으로 사용자 동작을 확인했다고 판단하지 않는다. 세부 로그를 모두 복사하기보다 판단에 필요한 근거를 유지한다.

담당자가 갱신한 기능 문서·wiki를 코드와 검증 근거에 대조한다. 확인한 공통 색인 제안을 메인이 취합해 반영한다. 색인에는 기능 설명과 기능 문서·wiki·코드·검증 방법으로 가는 연결을 둔다. 문서에는 현재 동작, 설계 이유·제약, 근거 파일과 실제 검증 명령·결과, 미확인 사항을 필요한 만큼 남긴다. 검증한 커밋이 있으면 식별자를 기록하고 커밋 전 작업이면 확인 날짜와 변경 파일을 기록한다. 다음 위임에는 갱신한 색인과 해당 기능 문서 경로를 전달한다. 문서 갱신과 관련 링크 확인도 완료 기준에 포함한다.

관련 범위의 누락·실패가 있으면 기존 명세와 확인한 문제를 같은 담당자에게 전달해 보완하도록 한다. 새 담당자가 필요한 경우는 기존 담당자가 작업할 수 없거나 독립된 책임이 생겼을 때로 한정하고 소유권을 다시 정한다. 사용자 요구가 바뀌었다면 바뀐 범위와 완료 기준을 명세에 반영한다.

미확인을 충족으로 바꾸거나 구현에 맞춰 완료 기준을 낮추지 않는다. 필요한 검증을 실행할 수 없으면 완료한 부분과 검증 불가 이유, 남은 작업을 구분해 보고한다. 사용자에게 최종 결과와 검증 근거, 한계, 요청 범위에 포함된 제출 위치를 짧게 전달한다.
