# 구현 작업 명세

요청 검증을 마치고 구현을 위임할 때 사용한다. 작은 수정은 각 항목을 한두 문장으로 작성하고 해당하지 않는 항목은 생략하되, 완료 기준과 결과 확인 기록은 유지한다. 표 대신 짧은 항목으로 기록해도 된다. 훅이 현재 작업의 기록 컨텍스트를 제공하면 [실행 가능한 완료 기록](completion-record.md)의 `init`으로 기준을 고정하고 결과를 같은 컨텍스트에 기록한다. 아래 표와 대화는 설명용이며 실행 기록을 대신하지 않는다. 훅이 없는 진행 중 작업은 표나 짧은 항목으로 수동 대조한다. 사용자 요구와 메인의 해석·가정을 분리한다. 목적과 우선순위는 확인한 대화와 근거에서 가져오고, 빈 항목을 채우기 위해 만들지 않는다. 진행을 막는 미정 사항은 위임 전에 해소한다.

## 전달 형식

```text
작업 목적
- 누가 어떤 상황에서 겪는 문제를 왜 해결하려는지 적는다.

기대 결과와 기능
- 사용자가 경험할 변화와 각 기능이 그 변화에 어떻게 기여하는지 적는다.

완료 기준
- 구현 전에 고정 ID, 종류(behavior/design/analysis), 구체적인 통과 조건, 확인 방법을 적는다. 구현에는 설계 기준을 최소 하나 포함하고 분석은 분석 기준을 쓴다.
- 적용되는 동작 기준과 설계·책임·상태 소유권 기준을 구분한다.
- 사용자 승인으로 범위를 바꿀 때 원래 ID와 변경 이유를 남긴다.

판단 우선순위와 제외 범위
- 요구가 충돌하거나 선택이 필요할 때 적용할 확정된 우선순위와 근거를 적는다.
- 이번 작업에서 제외하기로 한 범위를 적는다.

사용자 요구와 제약
- 사용자가 확정한 요구와 변경하면 안 되는 동작을 적는다.
- 로컬 작업, 커밋, 푸시, PR 등 허용된 작업 범위를 적는다.

작업 범위와 파일 소유권
- 저장소와 작업 트리, 담당 파일 또는 모듈을 적는다.
- 다른 담당자의 소유 범위와 공유 작업의 관리자를 적는다.

확인한 사실과 근거
- 관련 코드·설정 위치와 확인한 현재 동작을 적는다.
- 적용할 프로젝트 지침과 검증 명령을 적는다.

가정과 미확인 사항
- 메인의 해석과 아직 조사하지 않은 사실을 구분한다.
- 담당자가 조사할 항목과 사용자 결정이 필요한 조건을 적는다.

구현 전 책임·소유권
- 신규 기능이나 여러 책임을 바꾸면 독립적인 변경 이유, 담당 모듈, 원본 상태 소유자와 갱신 경로, 호출자 계약을 짧게 연결한다.
- 적용되는 설계 통과 조건을 완료 기준 ID와 연결한다. 작은 수정은 기존 담당과 영향 확인으로 충분하다.

구현과 검증
- 코드베이스 설계 스킬을 적용하고 실제 코드와 명세를 대조한다.
- 명세의 오류나 중요한 누락은 메인에 보고한다.
- 실행 동작의 구현·수정은 debug-verify에 따라 사용자 흐름과 실제 값을 대조하고, 관련된 비동기 응답 순서·상태 생명주기를 확인한다.
- 문서·지침 변경은 실제 산출물·참조·주입 결과로 검증한다.
- 완료 기준에 필요한 검증과 프로젝트 필수 검사를 수행한다.
- 사용자와 다른 담당자의 변경을 보존한다.

반환 결과
- 변경 요약과 파일 위치
- 처음의 모든 완료 기준 ID별 충족·미충족·미확인 및 실제 검증 근거
- 문제 ID별 원래 범위·해소 조건과 현재 처리 상태
- 미완료·미검증 항목과 필요한 사용자 결정
- 맡긴 제출 작업의 확인된 위치와 상태
- 현재 담당자 컨텍스트의 result/check 결과와 기록 위치. 메인은 이를 자신의 검토와 구분한다.
```

## 완료 기준과 문제 기록

위임 전에 ID·종류·통과 조건·확인 방법을 정하고, 결과 회수와 보완 과정에서 나머지를 갱신한다. 메인의 재확인은 담당자의 자기 보고와 구분한다.

| 기준 ID | 종류 | 구체적인 통과 조건 | 확인 방법 | 상태 | 실제 근거 | 메인 재확인 |
| --- | --- | --- | --- | --- | --- | --- |
| C1 | behavior/design/analysis | 사용자가 확인할 동작 또는 설계 조건 | 실행·관찰 또는 코드·호출부 검토 | 미확인 | 확인한 위치·명령·관찰 결과 | 확인 결과와 근거 |

발견한 문제는 아래 기록에 별도로 남긴다. 문제가 없으면 `미해결 항목 없음`으로 명시한다. 보완 요청·일부 수정 상태에서는 문제를 열린 상태로 유지하고, 현재 산출물에서 원래 범위 전체를 메인이 재확인한 뒤에만 해결로 닫는다.

| 문제 ID / 관련 기준 ID | 원래 문제의 범위와 해소 조건 | 현재 상태와 남은 작업 | 메인 재확인 근거 |
| --- | --- | --- | --- |
| F1 / C1 | 무엇이 잘못됐고 어떤 결과여야 해결인가 | 미해결·부분 보완·해결 및 남은 범위 | 현재 산출물의 위치·관찰 결과 |

## 결과를 해석하는 기준

명령 실행 여부와 검증한 동작을 구분한다. 소스 확인, 단위 테스트, 실제 앱이나 외부 시스템에서 관찰한 근거를 구분해 반환한다. 빌드·동작 확인으로 설계·책임·상태 소유권 검토를 대체하지 않는다. 검증 실패는 원인과 보완 상태를 적고, 검증 불가는 실행 조건과 남은 확인을 적는다. 수정으로 근거가 더 이상 유효하지 않으면 관련 기준과 문제를 다시 확인한다.

메인은 완료 보고 전에 처음의 모든 기준 ID와 결과 기록을 대조해 누락을 검사하고, 각 기준의 상태·근거·메인 재확인과 미해결 문제 목록을 점검한다. 필수 기준의 누락·미충족·미확인이나 미해결 문제가 있으면 보완을 요청한다. 계속 진행할 수 없다면 미완료와 남은 항목을 보고한다. 사용자 승인 없이 기준을 삭제·완화하거나 미확인을 충족으로 바꾸지 않는다.
