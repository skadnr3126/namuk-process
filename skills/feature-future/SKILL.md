# 개발자의 이해와 변경 판단

사용자가 이 스킬을 명시적으로 호출했을 때만 실행한다. 기능 구현의 완료나 변경 규모를 이유로 자동 실행하거나 메인 워크플로우·훅에서 자동 호출하지 않는다.

개발자가 해당 기능의 동작을 설명하고, 변경 위치와 영향을 판단하며, 실패 시 확인할 근거를 찾을 수 있도록 돕는다. 모든 내부 구현을 숙지하는 것을 목표로 삼지 않는다. 작업의 위험과 개발자가 맡을 책임에 따라 살펴볼 깊이를 조정한다.

## 설명 범위와 근거

사용자가 지정한 기능과 변경 범위를 확인하고 실제 코드, 호출부, 변경 내역, 관련 검증 결과를 읽는다. 변경 전후 비교는 확인 가능한 기준 버전을 사용하고, 이전 상태나 설계 의도를 알 수 없으면 추측을 사실로 쓰지 않는다.

핵심 설명에 파일 경로, 함수·타입 이름, 코드 위치, 관련 테스트나 실행 결과를 연결한다. 개발자가 설명에서 실제 코드와 관찰 근거로 이동할 수 있어야 한다. 확인된 사실, 분석·추론, 설계에 대한 견해, 미확인 사항을 구분한다.

이해 범위는 다음 세 단계로 정한다. 변경과 무관한 항목을 채우거나 함수·변수·필드를 빠짐없이 나열하지 않는다.

| 범위 | 설명할 내용 |
| --- | --- |
| 지금 알아야 할 것 | 기능의 목적과 변경 전후 동작, 주요 실행·데이터 흐름, 모듈의 책임과 연결, 데이터·상태의 소유자와 생명주기, 지켜야 할 조건, 설계 선택의 이유와 한계 |
| 변경할 때 찾을 수 있어야 할 것 | 수정할 모듈과 진입점, 영향을 받는 호출부, 관련 테스트, 실패를 확인할 로그·저장 데이터와 관찰 방법 |
| 필요할 때 조사할 것 | 내부 보조 함수, 라이브러리 구현, 현재 판단에 영향을 주지 않는 세부 알고리즘 |

호출자는 인터페이스를 올바르게 사용하는 데 필요한 입력·출력·호출 순서·오류 방식·제약을 알면 된다. 유지보수자는 변경을 맡을 때 해당 구현과 영향 범위를 더 깊게 살핀다. 직접 수정, 오류 추적, 성능·보안 판단에 내부 동작이 필요하면 세 번째 단계의 내용을 앞 단계로 올리고 그 이유를 설명한다.

## 설명과 설계 평가

먼저 기능의 목적과 핵심 변화를 설명하고, 진입점에서 상태 변경이나 결과까지의 흐름을 따라 기존 시스템과 연결한다. 구조도, 데이터 흐름도, 변경 전후 비교는 글보다 이해에 도움이 될 때 사용한다.

설계 평가는 실제 코드와 구체적인 변경 시나리오에 근거한다. 책임, 의존성, 상태 관리, 검증 가능성을 살피고 현재 선택이 미래에 확보한 선택권, 제한한 선택권, 아직 남겨둔 선택권을 설명한다. 선택 이유가 기록되어 있지 않으면 평가와 작성자의 의도를 구분한다.

개선을 제안할 때는 해결할 문제, 얻는 이점, 비용과 복잡성, 개선이 필요해지는 조건을 함께 제시한다. 중요도와 시급도를 구분하고 당장 바꾸지 않아도 되는 이유도 고려한다. 가상의 모든 미래 요구에 대비하거나 불필요한 리팩터링을 권하지 않는다. 설명 요청을 코드 수정 권한으로 확대하지 않는다.

## 판단 가능한 설명의 완료 기준

산출물은 개발자가 다음 판단에 사용할 수 있는 설명과 근거를 제공해야 한다.

- 기능이 어디서 시작되어 어떤 흐름으로 결과를 만드는지 설명할 수 있다.
- 다음 요구사항을 적용할 위치와 영향 범위, 유지해야 할 조건을 찾을 수 있다.
- 예상과 다른 결과가 나오면 무엇을 관찰하고 어떤 코드·테스트·데이터와 대조할지 찾을 수 있다.
- 현재 설계의 선택권과 한계를 바탕으로 진행하거나 개선할 이유를 판단할 수 있다.

실제 변경에 맞는 짧은 실전 사례를 제공하고 판단 과정과 근거 위치를 함께 보여준다. 예를 들어 저장 기능이라면 “저장 방식을 바꿀 때 수정할 위치와 유지할 조건” 또는 “성공 표시 후 재시작하면 데이터가 없을 때 확인할 흐름과 저장 데이터”를 설명할 수 있다. 예시는 현재 코드에 맞게 고르고 존재하지 않는 로그나 검증 수단을 만들어 쓰지 않는다.

설명을 제공했다는 사실만으로 개발자가 이해했다고 결론 내리지 않는다. 사용자가 원하면 직접 설명하거나 작은 변경을 해보며 이해를 확인할 수 있지만, 시험·답변·실습을 요구하거나 다음 작업의 필수 조건으로 만들지 않는다.

다음 상태를 별도로 보고한다.

- **기능 검증:** 실제로 수행된 테스트·사용자 흐름과 결과, 회귀 위험, 미검증 동작. 코드를 읽은 결과를 실행 검증으로 표시하지 않는다.
- **이해 지원:** 제공한 설명과 근거, 남은 설명상의 공백. 사용자의 설명이나 실습 등 확인 근거가 없다면 이해 여부는 미확인으로 남긴다.

다음 단계의 권고는 근거에 맞춰 현재 구조로 진행, 특정 부분의 추가 이해, 필요한 구조 개선, 추후 개선 중에서 제시할 수 있다. 이해 미확인 자체를 진행을 막는 이유로 삼지 않는다.

## 산출물 선택

사용자가 지정한 형식을 우선한다. 짧거나 한 흐름에 국한된 변경은 대화에서 핵심 흐름과 코드 위치를 설명한다. 여러 기능·모듈이 연결되어 탐색과 접힌 상세 설명이 도움이 되면 HTML 리포트를 선택한다. 모든 항목을 같은 분량으로 설명할 필요는 없다.

HTML을 만들 때만 [HTML 리포트 구성](references/html-report.md)을 읽는다. 형식과 관계없이 위의 이해 범위, 근거 구분, 판단 기준과 검증 상태를 유지한다.
